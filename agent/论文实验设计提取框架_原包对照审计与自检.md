# 论文实验设计提取框架：原包对照审计与自检

> 审计对象：`agent-harness.zip`  
> 审计日期：2026-07-25  
> 审计目的：检查我此前对压缩包的理解是否存在缺漏、过度概括或自行添加，并说明原包如何对相关对象进行严格检验、评判、阻断和追溯。  
> 基线原则：以 ZIP 内文件为准。工作区中的解压目录存在大量未提交改动，因此仅用于辅助定位，不作为原包基线。

---

## 1. 审计结论

### 1.1 总体结论

我上一轮的总体方向基本正确：原包确实构建了一套围绕科研任务、证据、实验计划、实验执行、数据摄取、诊断、工程设计、Build/Test、科学评审和人工审批的结构化框架。

但是，上一轮回答把几个不同层次的能力合并成了一个比较顺滑的“论文全文 → 实验设计提取”叙述。严格对照代码后，需要作如下校正：

1. **原包没有实现完整的论文全文解析与实验设计抽取流水线。**
   - 已实现的是文献检索适配器接口、文献元数据对象、证据主张草稿对象、证据条件匹配、DOI 查询入口，以及下游实验/设计/评审对象。
   - 当前本地论文知识库中的 `experimental_evidence.json` 明确为空。
   - 因此，不能说原包已经拥有完整的“论文实验设计提取模块”；更准确的说法是：**原包为该模块准备了部分上游证据契约和大量下游消费、验证与治理结构，但核心的全文级实验设计抽取仍是空缺。**

2. **原包中的“实验设计”不是一个单一 Schema，而是分散在多个业务层。**
   - `ExperimentPlan`：项目账本层的实验计划。
   - `DiagnosticTest`：用于区分竞争假设的诊断实验。
   - `ExperimentalExecutionPlan`：诊断实验的执行草案。
   - `BuildTestPackage`：候选工程设计的 Build/Test 包。
   - `ExperimentRun`：真实执行记录。
   - `DataAsset` / `Observation`：原始数据与派生观察。
   - 上述对象有关联，但不能直接当成同一个“论文实验设计提取结果对象”。

3. **原包中的严格性主要体现在“状态迁移与下游使用限制”，不等于每个上游字段都有强校验。**
   - 部分规则是真正阻断式的 Gate。
   - 部分规则只返回 `revise`、`insufficient_evidence` 或 `human_review`。
   - 部分能力只是诚实标记 `unknown`、`not_reported`、`not_applicable`。
   - 还有一些接口存在，但没有被证明在所有文献证据入口上强制调用。

4. **我上一轮有少量自行加入的工程建议。**
   - “每个小模块先定义输入/输出 Schema，再独立验证”是合理工程方法，但不是原包逐字规定。
   - “模块尽量低耦合、可独立运行和替换”是我提出的实现原则，不是压缩包中的明确硬性要求。
   - “全部模块最后统一串联、端到端测试并打包”主要来自用户要求，不是原包自身的机制。

### 1.2 是否存在严重误读

没有把完全不存在的核心业务模块说成已经实现，但存在以下需要重视的**过度归纳**：

- 把“证据主张抽取字段”描述成了“完整论文实验设计抽取字段”。
- 把分散在不同对象中的控制、重复、采样、成本、风险字段合并成了一套统一 Schema。
- 把 DOI 验证入口描述得像全局强制门禁，实际代码只能证明该入口存在并可记录失败，不能证明所有文献进入系统前都必经该入口。
- 把“不可变、版本化”描述成全局绝对规则；实际是核心对象大量采用不可变/追加式设计，但不同模型允许修改的字段并不完全相同。

## 2. 原包中真正与“论文实验设计提取”有关的能力边界

## 2.1 已明确实现的上游文献与证据契约

来源：

- `harness/evidence_retrieval/contracts.py`
- `harness/evidence_retrieval/crossref_adapter.py`

### `EvidenceDocument`

原包为一个证据文档定义了以下信息：

- `source_id`
- `source_type`
- `title`
- `authors`
- `publication_year`
- `journal_or_repository`
- `doi_or_accession`
- `url`
- `abstract_or_summary`
- `raw_metadata`

这是一套**文献/知识库文档元数据契约**，不是完整论文结构解析结果。

### `EvidenceClaimDraft`

原包为从文档中抽出的单条主张定义了：

- `claim_summary`
- `organism`
- `strain`
- `genotype`
- `condition`
- `intervention`
- `comparator`
- `measurement`
- `direction`
- `effect_size_if_reported`
- `uncertainty_if_reported`

其 docstring 明确规定：

- 文献没有报告的信息不能猜测。
- 当抽取方法只是 `api_metadata_only` 时，只能使用书目 API 实际提供的信息。
- 缺失内容应保持 `not_reported`、空值或等价的显式未知状态。

### `EvidenceItem`

进入诊断/评审体系后的正式证据对象进一步保存：

- 来源类型和来源引用；
- 内容摘要；
- 条件和时间；
- 质量与直接性；
- 修正、替代和版本关系；
- 模型运行、实验运行、观察记录的关联；
- 文献题名、作者、年份、期刊、DOI；
- 物种、菌株、基因型；
- 干预、比较对象、测量指标、方向；
- 效应量与不确定性；
- DOI 验证状态；
- 抽取方法和抽取状态。

这说明原包对“证据主张”的承载结构比较完整，但它仍然主要是**claim/evidence 粒度**，不是完整的论文实验分组和方法学抽取 Schema。

## 2.2 明确没有实现或没有填充的部分

来源：

- `knowledge/papers/experimental_evidence.json`
- `knowledge/papers/paper_metadata.json`
- `README.md` 中的已知局限说明

事实如下：

- 示例论文只保存了少量元数据。
- `engineering_methods` 为空。
- `experimental_results` 为空。
- `experimental_evidence.json` 中每篇论文的 `results` 为空。
- 文件注释明确说明：尚未解析论文原文，因此不保存菌株、滴度、产率等具体实验点，以免虚构。

因此，原包当前不能被视为已经实现：

- PDF/HTML/XML 全文解析；
- Methods/Results 章节识别；
- Figure/Table/Supplement 联合读取；
- 一个论文内多实验、多组别、多时间点的层级化恢复；
- 实验组和对照组的统一结构化抽取；
- n 值、随机化、盲法、统计检验等通用实验设计字段的完整抽取；
- 抽取结果与原文页码、段落、表格单元格的精确定位；
- 全文级冲突消解；
- 一套专属于“论文实验设计抽取”的端到端评分基准。

这些都是后续独立模块需要明确补齐或明确不做的边界。

## 4. 原包如何进行严格检验与评判

## 4.1 总体方法：结构化 Gate，而不是靠提示词自觉

来源：

- `harness/workflow/gates.py`
- `harness/workflow/controller.py`
- `harness/workflow/definitions.py`
- `harness/workflow/contracts.py`

原包的核心纪律是：

1. LLM 或业务模块只能提出候选输出；
2. 状态迁移由程序控制器决定；
3. Gate 返回结构化 `GateResult`；
4. Gate 结果不是一个裸布尔值，而包含：
   - gate 名称；
   - 状态；
   - 违规项；
   - 修复动作；
   - 必要时指定下一状态；
5. 多 Gate 聚合采用固定顺序；
6. 聚合采用“最坏状态优先”；
7. 前序 Gate 已失败时，Human Gate 不能越权放行。

这比“让模型自检一下”严格得多，因为状态写入权不在模型。

## 4.2 基础七类 Gate

固定顺序：

1. `SchemaGate`
2. `IdentityGate`
3. `BiologicalRuleGate`
4. `EvidenceGate`
5. `ModelApplicabilityGate`
6. `CandidateDiversityGate`
7. `SafetyHumanGate`

### 4.2.1 `SchemaGate`

检查输出是否符合契约。

失败行为：

- 状态为 `fail`；
- 每个 Schema 错误形成结构化 violation；
- 要求修复输出；
- Schema 失败会主导聚合结果。

### 4.2.2 `IdentityGate`

当前实现只对基因类型目标查询已知基因注册表。

失败条件：

- gene canonical ID 不在参考注册表中。

重要边界：

- 反应、通路、代谢物和菌株 ID 并没有在该 Gate 中得到等强度验证；
- 代码注释明确说非 gene 目标会跳过。

所以不能把它描述成对所有生物实体都完成了统一合法性校验。

### 4.2.3 `BiologicalRuleGate`

检查：

- 必需基因无条件敲除；
- 宿主范围冲突；
- 同一基因的互斥操作；
- 某些风险操作是否已获人工批准。

处理方式：

- 宿主范围冲突和操作冲突可直接失败；
- 未批准的必需基因敲除进入人工审查；
- 已批准的高风险项仍保留 violation 记录用于审计；
- 替代方案必须作为新候选，而不是偷偷修改原候选。

### 4.2.4 `EvidenceGate`

检查：

- 诊断若声称存在瓶颈，是否有 `source_ddr_id`；
- 设计决策是否至少引用一个 `evidence_record_id`。

失败状态：

- `insufficient_evidence`；
- 要求附加证据，或降低置信度并标记需要验证。

**实现缺陷/局限：**

代码中“高置信度但无模型或文献支持”的分支写成：

```python
if not d.evidence_record_ids:
    ...
elif d.confidence == "high" and not d.model_prediction_ids and len(d.evidence_record_ids) < 1:
    ...
```

第二个条件中的 `len(...) < 1` 在 `elif` 分支实际上无法成立，因为能进入 `elif` 已代表 evidence 列表非空。因此：

- `missing_evidence` 检查有效；
- 但 `unsubstantiated_high_confidence` 这一预期检查在当前逻辑下基本不可达；
- 不能声称高置信度主张已经被该分支充分严格校验。

### 4.2.5 `ModelApplicabilityGate`

当前实现不是“没有模型就失败”。

实际行为：

- 有模型：`passed`；
- 没有模型：仍然 `passed`，但在 `required_actions` 中记录 `not_applicable` 和无机制模型的事实。

其严格性在于“不伪造模型结果”，而不是强制要求一定有模型。

### 4.2.6 `CandidateDiversityGate`

当前基础实现按 `(target, operation)` 去重。

相同目标和相同操作的候选会被判定为重复，并返回 `revise`。

边界：

- 该基础 Gate 的判重粒度较粗；
- 更复杂的机制/架构多样性由后续设计层 Gate 和 evaluator 承担。

### 4.2.7 `SafetyHumanGate`

规则：

- forbidden 风险直接失败；
- 强制人工审批的风险没有批准则进入 `human_review`；
- 前序 Gate 已失败时，人工审批不能绕过失败；
- 人工批准并不自动清除审计记录。

## 4.3 数据摄取与结果解释 Gate

### `DataIdentityGate`

要求每个样本映射到：

- 设计版本/构建体；
- 条件；
- 重复身份；
- 样本清单。

未映射样本会阻断生物学解释，不允许“带着警告继续解释”。

### `DataQCGate`

QC 失败时：

- 返回 `insufficient_evidence`；
- 要求重新处理、排除失败样本或将观察标为不确定；
- 技术/QC 失败不能自动转成生物学失败。

### `GenotypeVerificationGate`

构建体未验证时：

- 不允许把表型归因于计划基因型；
- 返回证据不足。

### `HypothesisUpdateGate`

假设更新必须包含：

- 预期结果与实测结果的比较；
- 竞争解释；
- 不确定性。

不允许直接从一个观察跳到确定结论。

### `PolicyUpdateGate`

区分：

- 项目内更新；
- 跨项目/全局策略更新。

跨项目更新要求更高证据量和人工审批。技术失败不能驱动跨项目生物学策略更新。

### `RedesignGate`

新设计必须说明相对父版本：

- 保留什么；
- 删除什么；
- 新增什么；
- 每项变化由哪个观察或假设更新触发。

与父版本完全相同的设计不能冒充新设计。

## 4.4 诊断实验的严格评判

### `DataSufficiencyGate`

检查：

- baseline；
- genotype/chassis；
- condition；
- temporal context；
- QC；
- key phenotype。

缺失太多时直接失败；部分缺失时不会把诊断包装成充分结论。

### `CompetingSetGate`

要求至少存在两个机制上有区别的竞争假设。

如果没有竞争集合，就不能宣称诊断已经 actionable。

### 判别性测试

`DiagnosticTest` 明确保存：

- 每个假设对应的预期结果；
- 阳性/阴性对照；
- 决策规则；
- 是否能区分假设；
- 信息增益、成本、周期、可用性、技术可行性和风险。

因此评判不是只看实验“是否可做”，还看其是否能够减少关键不确定性。

### 诊断停止与交接

原包还区分：

- 是否有致命矛盾；
- 是否有未解决的模型冲突；
- 排名是否稳定；
- 是否仍有高价值测试；
- 是否达到可行动、证据受限或需人工评审状态。

工程价值评估在诊断停止之后进行，避免用“工程上很想做”反向污染诊断证据判断。

## 4.5 执行计划 readiness 评判

### 诊断执行计划

`execution_planner.assess_readiness()` 要求以下字段：

- 协议引用或草案；
- 材料；
- 对照；
- 采样计划；
- QC 验收标准；
- 预期输出 Schema；
- 解释规则；
- owner。

缺失时只能是 `conceptual` 或 `draft`，不能声称 `ready`。

### Build/Test readiness

`BuildReadinessGate` 检查：

- construction concept；
- materials；
- controls；
- replication plan；
- sampling plan；
- QC checkpoints；
- decision rules；
- protocol or draft。

缺失任何一项：

- 返回 `revise`；
- readiness 最多为 `planning_ready`；
- 每个缺失项进入 required actions。

**实现边界：**

- `build_test_planner.py` 中 `has_protocol_or_draft` 直接复用了 `bool(construction_concept)`，没有独立协议字段参与判断；
- `required_capabilities_or_instruments` 会用于资源匹配和缺失资源计算，但没有作为 `BuildReadinessGate` 的独立必填布尔项；
- 所以 readiness 严格，但并非已经覆盖所有现实执行细节。

## 4.6 证据条件匹配

来源：`harness/evidence_retrieval/condition_matching.py`

匹配维度：

1. organism
2. strain
3. genotype
4. medium
5. condition
6. timepoint
7. intervention
8. measurement

单维结果：

- `match`
- `mismatch`
- `unknown`

总体结果：

- `direct_match`
- `close_match`
- `partial_match`
- `cross_strain`
- `cross_species`
- `condition_mismatch`
- `endpoint_mismatch`
- `insufficient_metadata`
- `not_applicable`（模型词表包含，但主计算路径不一定生成）

关键优先级：

- organism 不同 → `cross_species`
- strain 不同 → `cross_strain`
- measurement 不同 → `endpoint_mismatch`
- condition/medium 不同 → `condition_mismatch`
- 8 个维度中至少 5 个未知 → `insufficient_metadata`
- 至少 6 个匹配且未知不超过 1 → direct/close
- 至少 4 个匹配 → close
- 其他情况 → partial

严格性：

- 跨物种/跨菌株证据不能自动当直接证据；
- 缺字段产生 transfer risk；
- mismatch 和 unknown 都会留下原因；
- directness 只有满足 direct match 且证据本身 direct 时才是 direct。

局限：

- 字符串匹配基本是标准化后的完全相等，不是复杂本体映射；
- 时间点和条件的语义归一化能力有限；
- 该规则评估的是可迁移性，不证明主张真实。

## 4.7 DOI 与引用真实性

来源：

- `harness/evidence_retrieval/service.py`
- `harness/evidence_retrieval/crossref_adapter.py`

`verify_doi()` 会：

- 调用 Crossref 解析 DOI；
- 无法解析时返回 `False`；
- 写入 `GEN_HALLUCINATED_REFERENCE_REJECTED` 项目事件；
- 让伪造/无效引用留下审计轨迹。

需要校正：

- 从现有代码只能确认存在真实 DOI 查询和失败记录入口；
- 不能据此断言所有文献证据在持久化前都被全局强制验证；
- 正式新模块若要“严格按照原包精神”，应把 DOI/来源验证明确接入状态迁移或导入 Gate，而不能只提供一个可选函数。

## 4.8 科学评审层

来源：

- `harness/scientific_evaluation/deterministic.py`
- `harness/scientific_evaluation/evidence.py`
- `harness/scientific_evaluation/model_eval.py`
- `harness/scientific_evaluation/critic.py`
- `harness/scientific_evaluation/comparator.py`
- `harness/scientific_evaluation/meta_review.py`
- `harness/scientific_evaluation/revision.py`
- `harness/scientific_evaluation/human_gate.py`

### 八类确定性规则

原包定义了八个版本化检查：

1. `DET-001`：Schema/内容完整性；
2. `DET-002`：引用合法性；
3. `DET-003`：冻结上下文一致性；
4. `DET-004`：硬约束；
5. `DET-005`：模型结果真实性；
6. `DET-006`：Build/Test 计划完整性；
7. `DET-007`：Human Gate 合法性；
8. `DET-008`：禁止绕过未解决 critical finding。

其中：

- 初始确定性检查先执行 `DET-001` 至 `DET-006`；
- Human Gate 前执行 `DET-007` 和 `DET-008`；
- `fail` 且 severity 为 `major` 或 `critical` 时阻断推进；
- 每条结果都有 rule ID、版本、类别、状态、严重度、影响字段、规则/证据引用和修复建议。

### `DET-006` 对实验计划的检查

当候选声称达到 planning/build readiness 时，必须存在 `BuildTestPackage`，且必须具有：

- controls；
- replication plan；
- sampling plan；
- QC checkpoints；
- decision rules。

缺失时为 `major fail`。

### 证据质量评估

科学评审层会保存：

- source quality；
- independence；
- host match；
- genotype match；
- condition match；
- process match；
- time match；
- intervention match；
- measurement match；
- mechanism match；
- directness；
- opposing evidence；
- applicability limits；
- over-extrapolation flags；
- overall strength；
- reasoning summary。

严格纪律：

- 没有证据的主张生成显式 unsupported/unknown 记录；
- 不会为了填满引用而自动生成文献；
- 知识库没有条件元数据时保持 `unknown`；
- 过去失败/拒绝的相同设计签名会作为 opposing evidence，并可能降低证据强度。

局限：

- 当前大部分知识条目缺少培养基、碳源、氧、温度、规模、时间点等信息；
- 大量匹配维度只能是 `unknown`；
- 当前评审器主要是确定性规则，不是实时第二模型或第二供应商独立复核。

### 模型结果诚实归一化

模型/工具结果区分：

- `computed`
- `not_computed`
- `unavailable`
- `failed`
- `out_of_domain`
- `stale`

不允许把 unavailable/not computed 包装成有效预测。

### Scientific Critic

原包实现：

- generalist critic；
- 按条件触发的 metabolic、genetic buildability、experimental design、process scale、safety/ethics critic；
- 不相关领域不会为了“形式完整”生成空泛评价；
- 每个 finding 具有类别、严重度、证据、反证、替代解释、证伪条件、所需动作、是否阻断和是否可解决。

诚实边界：

- critic 实际是确定性 rubric engine；
- 配置中的 LLM provider/model 会被记录，但代码明确写明没有调用；
- `shared_model_risk=True`；
- `model_independent=False`；
- 不能宣称已经完成真正的独立模型复核。

### Meta-review

规则：

- 不进行简单多数投票；
- 任意 reviewer 留下的开放、阻断性 critical finding 都会阻止进入 planning/build；
- 显式保存 reviewer 一致与分歧；
- 正向与负向建议冲突时要求人工裁决；
- 候选比较使用多维向量和 Pareto 思路，而不是把所有目标压成一个不透明总分。

### Revision

- finding 映射为 RevisionTask；
- 修订创建新候选版本；
- 原候选不被原地覆盖；
- 达到修订轮次上限后转人工审查，不能无限循环，也不能静默放行。

### Human Gate

规则：

- Agent 只能推荐；
- 最终科学决策由已识别的人类角色记录；
- proposer 不能批准自己提出的候选；
- approve 前重新执行确定性检查；
- critical/major 失败不能被 Human Gate 绕过；
- 决策、条件、理由、已知风险和时间都写入事件账本。

## 5. 原包如何保证可追溯、不可静默覆盖

## 5.1 追加式事件账本

原包通过 `ProjectEvent` 和各业务事件类型记录：

- 谁创建或修改了什么；
- 使用了哪个对象版本；
- Gate 为什么失败；
- DOI 为什么被拒绝；
- 哪个证据支持或反驳了哪个假设；
- 哪次人工审批允许或拒绝推进；
- 哪个 revision task 产生了新版本。

## 5.2 版本化与不可变对象

典型设计包括：

- `DesignVersion` 变更产生新版本；
- `HypothesisVersion` 追加新版本；
- `HypothesisAssessment` 通过 parent 引用追加；
- `BuildTestPackage` 大部分字段不可变，只允许有限状态字段变化；
- 科学评审、finding、meta-review 和人工决策单独持久化。

需要精确表述：

- 原包采用的是“核心科研对象尽量不可变、修订产生新记录”的总体纪律；
- 并非数据库中每张表的每个字段都绝对不可修改；
- 各模型通过 `guard_immutable_fields(..., mutable_fields=...)` 定义具体例外。

## 5.3 计划、执行、原始数据与解释分离

这是原包最值得继承的结构：

```text
ExperimentPlan
    ↓
ExperimentRun
    ↓
DataAsset
    ↓
Observation
    ↓
EvidenceItem / EvidenceLink
    ↓
HypothesisAssessment / ScientificEvaluation
```

其防止的错误包括：

- 把计划当作真实执行；
- 把协议草案当作已经完成；
- 把文件当作已经通过 QC 的观察；
- 把技术失败当作生物学阴性证据；
- 把一致性当作因果证明；
- 把单次观察直接升级为跨项目规律。

## 6. 原包中的测试与判定策略

相关测试目录包括：

- `tests/workflow/`
- `tests/projects/`
- `tests/diagnosis/`
- `tests/engineering_design/`
- `tests/scientific_evaluation/`
- `tests/llm_generation/`
- `tests/golden_set/`
- `tests/orchestrator/`

测试层次包括：

### 6.1 Gate 单元测试

逐个检查：

- 合法输入是否通过；
- 缺字段是否失败；
- 风险操作是否进入人审；
- failed Gate 是否不可被后续批准绕过；
- 数据身份/QC/基因型验证是否阻断解释；
- 缺失 Build/Test 要素是否降低 readiness。

### 6.2 状态机测试

检查：

- 非法状态迁移被拒绝；
- 只有 Controller 能写 current state；
- waiting 状态可跨进程恢复；
- 重试和修订存在上限；
- 人工审批前不能进入后续状态。

### 6.3 端到端案例

包括：

- 诊断闭环；
- 工程设计闭环；
- 科学评审闭环；
- orchestrator 全生命周期；
- 合成生物学示例案例；
- DBTL 数据摄取和学习。

### 6.4 Golden Set

原包存在 golden-set 数据结构、评分、runner 和人工审核模板。

但应注意：

- 该 Golden Set 面向更广泛的系统行为；
- 当前没有证据证明它已形成专门针对“论文全文实验设计抽取”的成熟标注集；
- 因此后续模块需要自己的字段级、关系级、证据定位级和拒答/未知处理基准。

### 6.5 多次一致性测试

存在五次运行一致性等测试，用于检查确定性状态机和规则是否稳定。

它验证的是：

- 规则和流程的可复现性；
- 不是 LLM 全文抽取结果天然稳定。

后续若核心抽取使用 LLM，需要额外设计：

- 固定输入下的结构一致性；
- 多次抽取共识；
- 原文证据定位一致性；
- 不确定性与 abstention 一致性。

## 8. 我上一轮遗漏的重要内容

上一轮没有充分说明以下严格机制：

1. Gate 采用固定顺序和最坏状态优先。
2. SchemaGate 失败时，后续 Gate 的检查不应产生误导性结论。
3. Human Gate 不能绕过早先失败。
4. 数据身份不清时直接禁止生物学解释。
5. 基因型未验证时禁止将表型归因于计划设计。
6. 技术失败不得升级为生物学负证据。
7. 假设更新必须显式考虑竞争解释和不确定性。
8. 跨项目知识更新需要更高证据门槛和人工批准。
9. 判别实验必须预声明不同假设下的预测结果和决策规则。
10. 诊断证据判断和工程价值判断被结构性分离。
11. 模型冲突不得平均或投票抹平。
12. 模型 unavailable/not computed 必须诚实保存。
13. Scientific Critic 实际是确定性规则引擎，不能宣称真正的模型独立性。
14. Meta-review 禁止多数投票掩盖 critical finding。
15. proposer 不能自批准。
16. 修订必须产生新版本，且有修订轮次上限。
17. 当前本地知识库的条件信息极不完整，大量匹配只能诚实返回 unknown。
18. 当前实验设计提取缺少全文原文定位和专用 golden set。

## 9. 原包自身存在的关键局限与潜在薄弱点

这些不是对原包的否定，而是后续模块必须避免误称“已经解决”的部分。

### 9.1 没有完整论文全文解析

没有看到成熟的：

- PDF layout parser；
- XML/JATS parser；
- 表格结构恢复；
- 图注/补充材料联合解析；
- 章节级定位；
- 原文 span/page/table-cell provenance。

### 9.2 文献检索不等于实验设计抽取

Crossref 主要提供书目信息，不能替代全文 Methods/Results。

`EvidenceClaimDraft` 是 claim 粒度，不能天然表达：

- 一个论文包含多少实验；
- 每个实验有哪些组；
- 哪些样本属于哪一组；
- 因素组合与时间序列；
- 哪个结果对应哪个组间比较。

### 9.3 缺少统一实验设计层级

当前对象分散在多个模块，尚缺类似以下统一关系：

```text
Paper
 └─ Study
     └─ Experiment
         ├─ Cohort/Arm/Group
         ├─ Intervention
         ├─ Comparator
         ├─ Sample
         ├─ Timepoint
         ├─ Assay
         ├─ Outcome
         └─ Result
```

这不是要求我们一定采用上述命名，而是说明当前原包没有一套统一层级完成这件事。

### 9.4 EvidenceGate 的高置信度分支不可达

前文已说明，这是一个真实的逻辑薄弱点。后续不能照抄这一错误。

### 9.5 DOI 验证没有被证明是全局硬门禁

需要在新模块中明确：

- 哪些 source type 必须验证；
- 验证失败是拒绝、降级还是待人工确认；
- 无 DOI 的合法资料如何处理；
- preprint、专利、数据集 accession 如何验证。

### 9.6 Condition matching 较为基础

字符串完全相等不足以覆盖：

- 培养基别名；
- 菌株谱系；
- 单位换算；
- 时间范围；
- 剂量范围；
- 温度近似；
- 过程规模；
- assay 同义词；
- endpoint 层级关系。

### 9.7 “未报告”与“未抽取到”需要进一步分离

原包有 `extraction_status`，但后续模块应严格区分：

- 文献明确未报告；
- 当前可访问文本中未发现；
- 信息只在补充材料；
- OCR/表格解析失败；
- 抽取器不确定；
- 不适用。

### 9.8 缺少论文抽取专用评测

需要单独定义：

- 字段准确率；
- group/intervention/outcome 关系准确率；
- 数值和单位准确率；
- 原文证据定位准确率；
- unknown/abstain 准确率；
- 跨正文/表格/补充材料的一致性；
- 幻觉引用率；
- 多次运行稳定性。

## 10. 后续小模块应如何“严格按照原包”

以下分为“必须继承的原包纪律”和“需要新增但不得冒充原包已有的能力”。

## 10.1 必须继承的纪律

1. **结构化输出**
   - 每个对象有显式 Schema；
   - 未知值有合法词表；
   - 禁止自由文本静默替代必填结构。

2. **来源可追溯**
   - 每个抽取字段尽量指向原文位置；
   - 保存文档 ID、版本、页码/段落/表格位置和抽取方法；
   - 派生结论不覆盖原始证据。

3. **不补造**
   - 未报告、未找到、解析失败、不适用必须区分；
   - 不根据常识补菌株、剂量、时间、重复数或统计信息。

4. **计划与执行分离**
   - 论文描述的 intended protocol 与 actual execution/deviation 分开；
   - 方法描述与结果观察分开。

5. **证据关系显式化**
   - 不把“结果一致”直接写成“证明机制”；
   - 支持、反驳、一致但不判别、无法区分分别记录。

6. **条件匹配**
   - organism、strain、genotype、medium、condition、timepoint、intervention、measurement 不得混合；
   - 跨物种/跨菌株证据自动降级；
   - 缺字段不得当匹配。

7. **Gate 控制状态**
   - 抽取器只生成候选；
   - Schema、来源、关系一致性、数值单位、证据定位和完整性 Gate 决定是否接受；
   - 人工审批不能绕过机器可确定的硬失败。

8. **版本化**
   - 修订生成新版本；
   - 保存父版本、变更原因和修订来源；
   - 旧版本可审计。

9. **诚实能力状态**
   - PDF 不可读、补充材料缺失、DOI 无法验证、表格无法恢复时明确记录；
   - 不得用貌似完整的结果掩盖能力缺失。

10. **测试与 Golden Set**
    - 单元测试 Gate；
    - 集成测试对象流转；
    - 端到端测试真实论文；
    - 人工标注集评估字段、关系、数值和 provenance。

## 10.2 必须新增但要明确标注为“新模块能力”

1. 论文全文摄取；
2. 文档结构恢复；
3. 实验/组别/样本层级；
4. 正文、表格、图注和补充材料联合抽取；
5. 原文 span/page/cell provenance；
6. 单位标准化但保留原值；
7. 同一论文内部冲突检测；
8. 未报告与解析失败的细分状态；
9. 论文实验设计抽取专用 Golden Set；
10. 字段级与关系级置信度；
11. 人工复核界面或可审计复核包。

这些能力符合原包方向，但不能在实现前写成原包已经具备。

## 11. 建议的后续验收口径

为了避免再次出现“合理归纳被误写成已有实现”，后续每个小模块的交付报告建议固定分为：

### A. 原包直接要求

- 对应原文件；
- 对应类、字段、Gate 或测试；
- 本模块如何原样继承。

### B. 为补齐空缺而新增

- 原包中不存在什么；
- 为什么本模块必须增加；
- 增加后如何保持兼容；
- 不把新增能力冒充为原包原有能力。

### C. 明确不做

- 本模块不处理的文档类型；
- 不处理的实验设计维度；
- 不保证的推断；
- 何时输出 unknown/unsupported/needs_review。

### D. 严格测试

- 正常案例；
- 缺字段案例；
- 冲突案例；
- 无 DOI/错误 DOI；
- 跨物种/跨菌株；
- 表格与正文不一致；
- 数值单位异常；
- 补充材料缺失；
- 多实验混淆；
- 幻觉诱导；
- 重复运行一致性；
- 人工复核案例。

## 12. 最终自我约束

后续开发中，我将采用以下约束：

1. 不再用“原包已经实现”描述仅存在接口或下游 Schema 的能力。
2. 每个结论标明是：
   - 原包已有；
   - 原包部分已有；
   - 原包占位；
   - 为本项目新增。
3. 先对照 ZIP 内原始代码，再参考工作区解压目录。
4. 不把分散在多个模型中的字段虚构成一个现成统一 Schema。
5. 不把可选 service 函数描述成全局强制 Gate。
6. 不把 `passed + not_applicable` 描述成完成了真实模型验证。
7. 不把 deterministic critic 描述成真正独立 LLM reviewer。
8. 不把空的论文实验知识库描述成已有实验结果抽取。
9. 每个小模块完成后，提供原包映射、增量说明、边界和测试证据。
10. 最终整合时保留所有 provenance、Gate result、版本和人工裁决记录。

---

## 13. 一句话结论

原包真正提供的是一套**“结构化科研对象 + 程序化 Gate + 追加式审计 + 版本化修订 + 人工最终裁决”**的严格治理框架；它为论文证据定义了部分抽取契约，但**尚未实现完整的论文全文实验设计提取**。后续模块应严格继承它的未知值纪律、证据关系、条件匹配、状态阻断和审计机制，同时把全文解析、实验层级恢复、原文定位与专用评测明确作为新增能力实现。
