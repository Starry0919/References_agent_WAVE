# 为什么升级到 v2（而不是继续用 v1 的措辞）

v1（`0730优化_1.md`）适合"检查有没有问题"，但当前阶段是**交给 Claude Code 自动执行的架构收口**，需要更强的约束：

1. **执行顺序**：必须先建立"设计文档 → 当前实现 → gap → 修复"的映射，再动代码，否则 Claude 容易直接改页面而跳过映射。
2. **压入设计文档的核心链路**，而不是简化成 "Paper → Knowledge Page"：

   ```
   论文 → 决策链 DDR → 规则蒸馏 → 知识检索 → 设计动作 → 评估器筛选 → 证据追溯 → 实验反馈
   ```
3. **检查"概念是否错位"**，不只是代码 bug。上一轮已经证实过一次：数据库里叫 `KnowledgeClaim` 的对象，语义不等于设计文档里的 Knowledge Claim（详见下方"v1 执行结果核对"）。
4. **明确哪些不该做**，防止 Claude 堆 UI、加字段，但偏离设计文档。

# v1 执行结果核对（写 v2 前必须先确认，不要重复建设）

对当前工作区代码做了核实，以下结论决定了 v2 每个 Phase 的起点：

| 项目 | 状态 | 依据 |
|---|---|---|
| DDR 空搜索返回全部记录 | ✅ 已实现 | `evidence_retrieval/local_ddr_adapter.py`、`test_local_ddr_adapter_search.py`（16 项新测试全部通过） |
| Design Knowledge Claim（区分实验知识 vs 设计知识） | ✅ 已实现，且**没有另建 schema** | `paper_extraction/rule_distillation.py::rule_as_knowledge_claim_view()` —— 以只读视图的方式把 `rules.json`（`source_ddrs` + `evidence_grading`）重塑成 claim 形状，函数文档明确写着"不要重复建设"。实验侧 `KnowledgeClaim`（`learning/models.py:142`，promotion ladder）保持不动，两者已经语义分离 |
| Applicability / Context Matching 报告 | ✅ 已实现（较薄） | `evidence_retrieval/service.py::assess_ddr_applicability()` + 前端 `ApplicabilityReportPanel.tsx`，输出 `matching_factors` / `transfer_risks` / `downgrade_reasons`，但目前只按 host + product 两个维度匹配 |
| 项目上下文（Project Context） | 🟡 部分实现 | `projects/models.py` 已有 `host_definition` / `target_product` / `objectives` / `constraints`（strain 嵌在 `host_definition` 里，没有独立字段）。但只有 `api/generation.py` 的证据检索和 `assess_ddr_applicability` 在读它，`engineering_design/*` 和 `evaluation/scientific_evaluation/*` **完全没有引用** |
| Design Decision → Rule 溯源 | 🔴 缺失 | `engineering_design/decision.py` 没有 `rule_ids`/`ddr_ids`/`evidence_ids` 字段；`evidence_resolution.py` 只解析到 `reference_id`（可指向 DDR），规则层完全没有接入；全仓库 grep `rule_id` 在 `api/generation.py` 中零命中 |
| Trust & Provenance Center | 🔴 缺失 | 前端没有 Trust Center 路由；已有的 `EvidenceProvenancePanel` / `ProvenanceLink` 是"单篇论文证据"粒度，不是"按 design_decision_id 查完整链路"的端点 |
| DDR JSON 字段完整度 | ✅ 已实现 | `knowledge/ddr_database/DDR-008_*.json` 的 `decision_chain[0]` 已包含 design_action / target / trigger / evidence / evidence_grading / evidence_grading_rationale / reason_nature / alternatives / implementation / result / rule，字段齐全 |

**结论**：v1 的 Phase 1（Knowledge Claim 语义修正）已经落地，v2 不应该再要求"新建 Design Knowledge Claim schema"，只需验证并把它在前端接完整。真正没做、且是设计文档核心的两块是：

- **Project Context 没有成为全系统共享状态**（Design、Evaluator 还是各自为政）
- **Design Decision 缺 rule_ids，Provenance 链条断在"规则"这一环**

v2 的 Phase 权重应该向这两块倾斜，而不是平均用力。

# Phase 2 — Project Context 成为全系统共享状态（本轮重点之一）

## 现状

`projects/models.py` 已有 `Project.host_definition` / `target_product` / `objectives` / `constraints`（strain 目前嵌套在 `host_definition` 里，没有提升为独立字段）。

但只有 `api/generation.py`（证据检索）和 `evidence_retrieval/service.py::assess_ddr_applicability()` 读取它。`engineering_design/*` 和 `evaluation/` `scientific_evaluation/*` 完全没有引用 `host_definition` / `target_product`。

## 要求

1. 判断是否需要把 strain 从 `host_definition` 提升为顶层字段（取决于设计文档 M0 的字段要求），给出结论并说明理由，不要两边都留。
2. 让 `engineering_design/`（策略生成、评估、portfolio 相关模块）和 `evaluation/` `scientific_evaluation/`（评估器）改为读取同一个 `Project` context 对象，而不是各自解析或忽略项目信息。
3. 避免每个模块自己重新定义一份 project context 的子集 —— 统一从 `Project` 模型取数据，不新建平行的 context 对象。

# Phase 3 — Knowledge Retrieval 相关性维度补全

## 现状

`evidence_retrieval/relevance.py::ddr_relevance()` 只产出 host_match / product_match 两个布尔值。`assess_ddr_applicability()` 在此基础上加了 `matching_factors` / `transfer_risks` / `downgrade_reasons` 文本解释，但维度仍然只覆盖 host + product，没有 mechanism 相似度和 design action（工程手段）相似度。

## 要求

不要改成硬过滤 —— 设计文档明确要求规则可跨产物迁移（例如丁醇规则迁移到脂肪酸）。

在现有 `matching_factors` 基础上补齐两个维度：

- **Mechanism**：机制相似度（例如 feedback inhibition release 是否匹配）
- **Engineering**：设计动作相似度（例如是否是同一类 design action）

返回结构继续保持"给分数 + 给理由"的形式，理由要能直接回答"为什么推荐这条 DDR/规则"。

# Phase 4 — Design Decision Provenance：补齐 rule_ids（本轮重点之一）

## 现状

`engineering_design/decision.py` 不含 `rule_ids` / `ddr_ids` / `evidence_ids`（目前只是 Pareto/portfolio 计算逻辑）。`evidence_resolution.py` 能把 `evidence_links` 解析到一个 `reference_id`（可能指向 DDR），但规则层完全没有接入这条链。`api/generation.py` 里没有任何 `rule_id` 相关字段。

## 要求

打通完整链条：

```
Design Decision → Rule → DDR → Paper → Evidence
```

具体修改：

1. `evidence_resolution.py`：在现有 `evidence_links` 解析基础上，新增对 `rule_ids` 的解析与校验（复用 `rule_distillation.py` 里 rule 记录的 `rule_id` / `source_ddrs`，不要另建规则存储）。
2. `decision.py` 或调用它的上层 schema：为设计建议增加 `rule_ids` 字段，与已有的 `evidence_ids` / `ddr_ids`（如果存在）并列。
3. `api/generation.py`：请求/响应中带上 `rule_ids`，确保生成的每条设计建议都能通过 `rule_ids → source_ddrs → 论文/证据` 追溯到底。
4. 前端：在 Design Workspace 展示设计建议时，附带其引用的规则（可以先做成简单列表，不需要复杂交互）。
5. 补充测试，覆盖"设计建议 → rule_ids → DDR → evidence"的完整解析路径。

# 收尾

这一版比 v1 长，但只在真正缺失的地方展开（Project Context 共享、rule_ids 溯源、Trust Center 最小闭环），已经做完的部分（DDR 空搜索、Applicability 报告、Design Knowledge Claim 视图）改成"验证一句话跳过"，避免 Claude Code 重复劳动或推翻已有实现。

三个必须压住的点，从 v1 的"语义重构"更新为：

1. **rule_ids 溯源链补齐**（Design → Rule → DDR → Evidence）—— 目前全仓库缺失，是设计文档"每条设计建议都要能回答为什么"的硬要求
2. **Project Context 变成全系统共享状态**（Design、Evaluator 目前不读）
3. **Trust Center 最小闭环**，且必须复用 Phase 4 的解析逻辑，不要另起一套

这三个不补，即使页面好看，从架构角度看仍然是"数据库展示"，没有达到 Agent 的核心设计。
