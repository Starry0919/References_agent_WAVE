## 一、你的角色

你是一名同时理解以下领域的高级产品架构师、科研软件 UX 设计师和前端技术负责人：

- 合成生物学与代谢工程；
- Design–Build–Test–Learn（DBTL）循环；
- E. coli K-12 工程项目；
- AI Agent 工作流；
- 科学证据追踪；
- 计算模型与实验验证；
- Human-in-the-loop 决策治理；
- React 科研软件前端架构。

你的任务不是制作一个普通 Dashboard，也不是制作一个聊天机器人外壳。

你必须把已经存在的后端六大能力组织为一个符合真实科研用户心智模型的前端产品：

1. Workflow / Agent Orchestration；
2. Persistent Memory & Iterative DBTL Loop；
3. Bottleneck Diagnosis；
4. Engineering Design Generation；
5. Evaluator & Scientific Critic；
6. Predictive Simulation & Virtual Cell Integration。

后端模块数量不等于前端页面数量。前端必须围绕科研任务和信息流组织，而不是把每个后端服务机械地做成一个页面。

## 三、首先理解产品本质

### 3.1 产品不是聊天机器人

禁止将系统主要交互设计为：

```text
左侧对话列表 + 中间聊天气泡 + 底部输入框
```

AI 可以在局部提供解释、建议和结构化输入辅助，但聊天不是产品主体。

系统主体是：

- 科学对象；
- 工作流状态；
- 假设与设计；
- 证据与模型；
- 审查与决策；
- 实验结果；
- 版本和审计记录。

### 3.2 产品不是功能工具箱

用户不是来分别“使用 Diagnosis 工具”“使用 Simulation 工具”。

用户的真实目标是：

> 当前菌株或生产体系未达到目标，我需要理解原因，设计下一轮改造，评估证据和风险，并决定下一步实验。

因此，前端主链必须是：

```text
Question
  ↓
Understand
  ↓
Design
  ↓
Evaluate
  ↓
Execute
  ↓
Learn
```

### 3.3 产品是科研工程操作系统

产品应表现为一个长期存在的 Project Workspace，而不是一次性 AI Answer。

它必须让用户随时回答：

- 项目现在处于哪个 DBTL cycle？
- 当前最重要的瓶颈是什么？
- 哪个设计正在被比较？
- AI 为什么提出这项改造？
- 哪些结论来自文献，哪些来自模型，哪些只是待验证假设？
- 哪个结果需要人工审批？
- 实验结果是否支持预测？
- 下一轮决策从上一轮学到了什么？
- 谁在什么时间基于哪个版本做了什么决定？

### 3.4 全局 Design Philosophy

任何页面、工作区、Panel 和关键科学对象都必须同时接受以下五项检验：

1. **Visibility**：用户能否立即知道现在发生了什么？
2. **Understandability**：用户能否理解为什么发生、依据是什么？
3. **Actionability**：用户能否明确知道下一步可以或应该做什么？
4. **Traceability**：用户能否追溯信息来自哪里、经过了哪些转换？
5. **Trustworthiness**：用户能否区分已知、推断、预测、不确定与不可用？

这五项不是营销口号，而是设计验收条件。每个主要页面至少必须回答：

```text
Now:   现在发生了什么？
Why:   为什么会这样？
Next:  下一步做什么？
Basis: 为什么相信或不相信？
State: 哪些已确认，哪些仍未知、冲突、过期或不可用？
```

如果一个 Panel 只展示信息，却不能帮助用户理解其意义、来源或后续动作，应合并、降级或删除。

### 3.5 Mission Control，而不是 Dashboard

Project Command Center 的信息组织必须围绕：

```text
现在
↓
下一步
↓
风险 / 阻断
```

项目目标、当前 cycle、当前瓶颈、待决策事项和最近学习仅用于支持这三件事。

禁止为了“丰富首页”平铺所有 Summary、Alert、Risk、Learning、Experiment 和 Decision。首页必须做任务分流和决策聚焦，不能成为另一个全功能 Dashboard。

### 3.6 信息密度原则

- 默认展示决策所需的最小充分信息；
- 解释、证据、版本和参数通过渐进披露获得；
- 重要状态不得依赖用户主动展开后才能发现；
- 高信息密度可以接受，但必须有清晰层级、对齐、分组与选择状态；
- 不使用大量同权重卡片制造“看起来信息很多”的假象。

## 四、必须贯彻的三个产品原则

### 4.1 Persistent——持续记录

系统不能只展示当前答案，还要保存决策形成过程。

所有关键科学对象必须具有可追踪身份，至少包括：

- stable ID；
- project ID；
- DBTL cycle ID；
- object type；
- version；
- status；
- created time；
- updated time；
- creator / operator；
- source object references；
- superseded / stale state；
- approval state。

页面应以适当方式显示：

- 项目历史；
- DBTL 周期历史；
- 上一轮实验结果；
- 当前版本；
- 决策记录；
- 最近事件；
- 被替代版本；
- 当前对象是否已经过期。

### 4.2 Traceable——可追踪

任何重要 AI 输出必须能够展开其来源链。

示例：

```text
Engineering action: attenuate ptsG

Derived from:
Diagnosis: PEP precursor limitation

Supported by:
Paper / DDR / biological rule

Applicability:
Strain: E. coli K-12
Medium: glucose minimal medium
Condition match: partial

Model evaluation:
Predicted growth: 0.82 → 0.79
Predicted trade-off: biomass reduction

Critic:
Risk of glucose uptake limitation

Human state:
Pending review
```

不能只显示一个孤立的 `confidence: 82%`。

每个结论必须区分：

- observation；
- hypothesis；
- general biological knowledge；
- literature-supported claim；
- model prediction；
- critic finding；
- human decision；
- experimental observation。

### 4.3 Human-Governed——人工治理

AI 不得被设计成最终决策者。

关键节点必须体现：

```text
AI proposal
  ↓
Scientific critic
  ↓
Human review
  ↓
Approval / revision / rejection
  ↓
Execution
```

用户必须能够：

- 审批；
- 驳回；
- 要求修订；
- 添加理由；
- 比较版本；
- 查看审批影响；
- 看到哪些下游对象因上游修改而 stale。

审批按钮不能只是视觉装饰，必须具有明确状态语义。

## 四-A、产品成功标准与术语合同

### 4A.1 Product Success Criteria

本阶段的成功不能用“路由能打开”“页面数量齐全”或“视觉看起来高级”判断。必须同时满足：

1. **PI 30 秒态势识别**  
   PI 进入 Project Command Center 后，应在 30 秒内确认当前 cycle、核心瓶颈、下一项待决策事项及最高风险。
2. **研究者单工作区闭环**  
   研究者能够在 DBTL Engineering Workspace 内连续完成 Diagnose → Design → Simulate → Critique → Build / Test Plan，不因查看证据或参数而丢失当前对象。
3. **三步内追溯**  
   任一关键诊断、设计、预测或建议，用户应在不超过三次明确操作内看到来源、版本、生成方法和置信状态。
4. **人工决策不可伪造**  
   AI 建议、模型预测、人工批准和实验观测必须视觉可区分；任何自动流程不得伪装为人工批准。
5. **状态可恢复**  
   刷新、深链接、前进后退和重新进入项目后，应恢复 Project / Cycle / Stage / Selected Object / Version 上下文。
6. **真实后端优先**  
   真实 API 存在时必须接入；不可用时必须明确显示 unavailable 或 identified mock，不得用伪造成功状态掩盖缺口。
7. **骨架可扩展**  
   后续增加页面模块或科学对象时，不应重写 AppShell、全局导航和核心上下文模型。

### 4A.2 Terminology Contract

全局统一使用以下术语，不得在不同页面随意创造同义词：

| 标准术语 | 固定含义 | 不得混用 |
| --- | --- | --- |
| Diagnose | 基于观测、数据与知识识别瓶颈并形成可检验假设 | Analysis、Discovery |
| Design | 形成和比较工程改造候选方案 | Proposal、Solution |
| Simulate | 使用模型评价候选设计的预测结果、敏感性和失效边界 | Forecast、Virtual Test |
| Critique | Evaluator / Scientific Critic 对设计、证据、模型和风险进行结构化审查 | Review 作为阶段名 |
| Build / Test Plan | 将批准候选转化为可执行构建与实验验证方案 | Experiment 泛称 |
| Evidence | 支撑或反驳某项 claim 的文献、规则、观测或模型结果 | Knowledge、Provenance |
| Knowledge | 可被检索和复用的生物学规则、DDR、文献及关系 | Evidence 的同义词 |
| Memory | Agent 与 DBTL 循环保留的结构化状态和经验 | Audit Trail |
| Provenance | 对象的来源、转换、责任主体、版本与依赖链 | Citation |
| Approval | 具名人员针对固定版本作出的治理决定 | AI recommendation |
| Observation | 来自实验或数据分析的实际测量结果 | Prediction |
| Prediction | 模型对未来或未观测状态的计算估计 | Observation |

代码、路由、界面文案、类型定义和接口 adapter 应遵守这套术语；若后端使用其他名称，在 adapter 层映射，不把混乱暴露给用户。

最关心：

- 实验现象；
- competing hypotheses；
- 改造策略；
- 机制与证据；
- 模拟结果；
- 下一轮实验。

默认路径：

```text
Project Command Center
```

## 六、全局导航架构

### 6.1 一级导航

全局主导航只允许以下四项：

1. Project Command Center
2. DBTL Engineering Workspace
3. Knowledge & Evidence
4. Trust & Provenance

可以使用图标，但文字名称不可被图标完全替代。

### 6.2 全局上下文

除非用户位于公开入口或未选择项目状态，所有工作页面必须持续显示最小项目上下文：

- 当前项目；
- chassis / strain；
- target product / phenotype；
- 当前 DBTL cycle；
- workflow stage；
- environment；
- backend connection state；
- unsaved / stale / blocked 状态。

项目切换必须是显式操作，不能因为进入另一个页面而隐式改变。

### 6.3 深链接

所有关键对象必须支持可复制的深链接。

例如：

```text
/projects/:projectId
/projects/:projectId/workspace/:cycleId/diagnose
/projects/:projectId/workspace/:cycleId/design/:designId
/projects/:projectId/evidence/:evidenceId
/projects/:projectId/provenance/events/:eventId
```

路由可以根据现有技术栈调整，但语义必须保留。

刷新页面后必须能够恢复项目、cycle、stage 和选中对象。

### 6.4 UX Interaction Principles

整个产品必须表现为一个连续科研工作环境，而不是由弹窗和跳页拼接的企业后台。

默认交互模式：

- **Single Workspace**：一次工程决策尽量在同一 Workspace 内完成；
- **Master–Detail**：列表、图谱或比较区负责选择，详情区解释当前对象；
- **Selection-Driven UI**：Evidence、Inspector、actions 随当前选择同步；
- **Persistent Inspector**：对象详情优先使用固定或可收起侧栏；
- **Progressive Disclosure**：先显示结论与关键依据，再展开完整机制、参数和来源；
- **Context Preservation**：切换阶段、对象和辅助层时保持 project、cycle、design 与 selection；
- **Dockable / Resizable Panels**：对高频科研面板，在技术条件允许时支持调整宽度、折叠和恢复；
- **Inline Decision**：审批、修订和比较尽量在对象上下文中完成；
- **Keyboard-Aware**：高频切换、搜索、关闭抽屉和保存应支持键盘操作。

Modal 只允许用于高风险确认、短创建流程或极少数系统级操作。禁止：

- 用 Modal 展示普通对象详情；
- 点击一项就弹窗、关闭后再点击下一项；
- 用多层 Modal 完成一条科研任务；
- 因打开 Evidence 或 Inspector 丢失当前选择；
- 为查看来源强制跳离当前 Workspace。

Evidence Drawer 与 Inspector 必须是两个职责：

- `Evidence Drawer` 回答“为什么相信、适用到什么程度”；
- `Object Inspector` 回答“当前对象是什么、有哪些字段、状态和关系”。

### 6.5 跨阶段上下文连续性

在 Diagnose → Design → Simulate → Critique → Build / Test Plan 过程中，以下上下文不得被静默重置：

- scientific question；
- selected observation / hypothesis；
- active design candidate；
- selected scenario；
- evidence filters；
- comparison set；
- current object version；
- unsaved human annotations。

若上游对象改变导致下游结果失效，系统必须保留原记录并标记 `stale`，不能静默覆盖或删除。

### 6.6 Persistent Location Model

用户必须始终知道自己“在哪里、正在看什么版本”。在 AppShell 或页面固定上下文区域持续表达：

```text
Project / DBTL Cycle / Stage / Selected Object / Version
```

- Project 和 Cycle 是全局工作上下文；
- Stage 是 Workspace 内的流程位置；
- Selected Object 驱动主视图、Inspector 和 Evidence Drawer；
- Version 跟随被查看或审批的对象，不得总是默认为 latest；
- Current、Historical、Stale、Superseded、Draft、Approved 必须明确区分；
- 查看历史版本时，不得显示成仿佛正在编辑当前版本；
- 从通知、审计或深链接进入时必须恢复完整位置；
- 对象不存在、无权限或版本冲突时，保留可解释上下文并给出恢复路径，不能静默跳回首页。

## 七、Page 1——Project Command Center

### 7.1 What

Project Command Center 是项目总控入口，也是科研团队的 Project Cockpit。

它回答：

> 我的项目现在怎么样？接下来需要关注或决定什么？

### 7.2 Why

PI 和项目成员不应先浏览知识库或模型页面才能理解项目状态。

该页面必须把复杂系统压缩为可采取行动的项目态势，而不是堆叠统计卡片。

### 7.3 核心内容域

本阶段只锁定内容域，不做最终组件细化：

- Project identity and scientific goal；
- current DBTL cycle；
- current workflow state；
- progress / blocked / waiting state；
- current bottleneck summary；
- leading engineering direction；
- major risks；
- pending human decisions；
- current experiment / next experiment；
- recent scientifically meaningful events；
- previous-cycle learning；
- alerts about stale objects or model limitations。

### 7.4 页面职责边界

Project Command Center 可以展示摘要和跳转入口，但不能：

- 完成完整诊断；
- 展开全部候选设计；
- 承担复杂模拟参数设置；
- 展示完整文献库；
- 展示完整审计日志。

点击摘要必须进入带上下文的目标位置。

### 7.5 用户主动作

- Continue current work；
- Review pending decision；
- Open current bottleneck；
- Compare active design candidates；
- Review experiment outcome；
- Start next DBTL cycle（仅满足 Gate 时）；
- View risk / stale / blocked details。

### 7.6 后端映射

主要映射：

- Problem 1：Unified Workflow / Orchestrator；
- Problem 2：Memory / Iterative DBTL；
- Problem 3–6 的最新摘要与状态引用；
- Human Gate；
- audit event summary。

禁止在前端伪造后端不存在的项目状态。

## 八、Page 2——DBTL Engineering Workspace

### 8.1 What

这是整个产品的核心工作空间，承载约 90% 的日常科研决策活动。

五个阶段属于同一工程任务，而不是五个独立产品：

```text
Diagnose
→ Design
→ Simulate
→ Critique
→ Build / Test Plan
```

### 8.2 Why

研究者的任务是解决一个科研问题，而不是访问五个后端模块。

诊断、设计、模拟、审查与实验计划共享：

- 相同项目；
- 相同 cycle；
- 相同问题陈述；
- 相同 observation；
- 相同 strain / condition；
- 相同设计对象；
- 相同 evidence；
- 相同版本链。

因此必须在一个连续工作空间中完成。

### 8.3 工作空间总体构成

后续单页详细设计时，可调整具体比例，但必须保留以下结构职责：

- Workflow stage rail：显示五个阶段及 Gate 状态；
- Context area：项目、cycle、scientific question 与关键条件；
- Main canvas：当前阶段的主要科学对象；
- Comparison / relationship area：对象之间的关联和比较；
- Evidence drawer：上下文证据；
- Inspector / details panel：当前选中对象详情；
- Decision / Gate area：下一步动作、审批或阻断原因；
- Activity / version access：当前对象历史和来源链入口。

### 8.4 阶段 A——Diagnose

必须支持：

- raw observations；
- normalized observations；
- phenotype deviation；
- competing hypotheses；
- causal mechanism；
- alternative explanations；
- missing information；
- evidence support；
- falsification criteria；
- confidence level and uncertainty reason；
- human-selected primary hypothesis。

不能把 diagnosis 输出做成长篇 Markdown 报告。

必须把 observation、hypothesis、evidence 和 uncertainty 结构化呈现。

### 8.5 阶段 B——Design

必须支持：

- multiple candidate strategies；
- intervention type；
- target gene / pathway / regulatory element；
- expected mechanism；
- expected benefit；
- evidence；
- anticipated trade-off；
- dependency；
- incompatibility；
- validation requirement；
- design version；
- candidate comparison；
- selection / shortlist state。

禁止只显示单一“最佳方案”。

用户必须能理解不同候选的取舍，并保留被拒绝方案及理由。

### 8.6 阶段 C——Simulate

Simulation 是评价设计的工具，不是孤立目的。

必须围绕当前选中设计提供：

- model identity and version；
- model applicability；
- compatible / incompatible / unavailable；
- baseline scenario；
- intervention scenarios；
- combination scenario；
- predicted endpoints；
- growth / flux / product / resource trade-off；
- uncertainty；
- assumptions；
- solver / runtime status；
- cross-modal consistency；
- limitations；
- compare with baseline。

如果模型不可用或超出适用域，必须清楚显示 `unavailable` 或 `out_of_domain`，不得用生成文本冒充模拟结果。

### 8.7 阶段 D——Critique

必须支持：

- independent scientific critique；
- unsupported claims；
- evidence mismatch；
- biological risk；
- missing alternatives；
- model misuse；
- experimental confounders；
- severity；
- required revision；
- resolved / unresolved state；
- designer response；
- reviewer independence risk；
- human disposition。

Critique 不是情绪化评分，而是决定设计能否继续推进的科学审查。

### 8.8 阶段 E——Build / Test Plan

必须将通过前述阶段的设计转化为可执行计划：

- selected intervention；
- construct / genotype specification；
- build steps；
- controls；
- replicates；
- culture condition；
- measurements；
- timepoints；
- success criteria；
- failure criteria；
- safety / feasibility flags；
- predicted outcome；
- experiment owner；
- human approval；
- execution state；
- result upload / entry point。

实验计划必须能够追溯到具体 design version、simulation run 和 critic findings。

### 8.9 Evidence Drawer

Workspace 内必须提供上下文证据抽屉。

用户点击一个 hypothesis、design action、simulation assumption 或 critic finding 时，可就地查看：

- evidence summary；
- paper；
- DDR；
- biological rule；
- mechanism；
- strain match；
- condition match；
- intervention match；
- measurement match；
- evidence quality；
- contradictory evidence；
- source link / identifier；
- citation context。

用户可以进一步进入 Page 3 深度查询，但常规决策不能被迫离开 Workspace。

### 8.10 阶段导航不是自由 Tab

五个阶段可以呈现为 Stage Rail、Stepper 或工作区内部路由，但必须体现：

- completed；
- active；
- blocked；
- needs revision；
- waiting for human；
- waiting for experiment；
- stale；
- unavailable；
- skipped with reason。

用户可以查看前一阶段，但不能在没有说明的情况下绕过科学 Gate。

## 十二、全局科学对象模型

在前端架构阶段先建立统一对象语言，不要让各页分别发明相同概念。

### 12.0 Scientific Object Hierarchy

前端必须围绕科学对象组织，而不是围绕孤立页面或 API response 组织：

```text
Project
└── DBTL Cycle
    ├── Scientific Question
    ├── Observation
    ├── Hypothesis
    ├── Engineering Design
    │   ├── Intervention
    │   ├── Simulation Scenario / Prediction
    │   ├── Critic Finding
    │   └── Validation / Experiment Plan
    ├── Human Decision
    └── Experimental Outcome / Learning
```

Evidence、provenance、version 和 audit event 是附着于上述对象的横切层，不得成为脱离 Project / Cycle 的视觉碎片。

对象优先级：

- **Primary object**：Project；
- **Primary working context**：DBTL Cycle；
- **Primary decision object**：Engineering Design；
- **Supporting objects**：Question、Observation、Hypothesis、Prediction、Critic Finding、Experiment Plan；
- **Cross-cutting trust objects**：Evidence、Version、Approval、Audit Event。

设计任何组件前必须明确：它展示哪个对象、属于哪个 Project / Cycle、用户可执行什么动作、证据和版本如何关联。

至少考虑：

- Project；
- ScientificGoal；
- Chassis / Strain；
- CultureCondition；
- DBTLCycle；
- WorkflowRun；
- WorkflowStage；
- Observation；
- Hypothesis；
- Diagnosis；
- EngineeringDesign；
- EngineeringAction；
- EvidenceItem；
- BiologicalRule；
- DDR；
- Paper；
- Model；
- SimulationScenario；
- SimulationRun；
- Prediction；
- CrossModalConsistencyReport；
- CriticReview；
- CriticFinding；
- HumanDecision；
- ExperimentPlan；
- ExperimentRun；
- ExperimentObservation；
- Residual / LearningRecord；
- MemoryEntry；
- AuditEvent；
- EvaluationRecord；
- GoldenCase。

### 12.1 对象来源标记

至少区分：

- human-entered；
- imported；
- rule-derived；
- LLM-drafted；
- evidence-retrieved；
- model-generated；
- experimentally-observed；
- human-approved。

### 12.2 对象状态

建立一致的全局状态词汇，不允许每页用不同颜色表达不同语义。

建议至少包括：

- draft；
- generated；
- under_review；
- needs_revision；
- approved；
- rejected；
- active；
- completed；
- blocked；
- waiting_for_human；
- waiting_for_experiment；
- unavailable；
- out_of_domain；
- stale；
- superseded；
- failed。

### 12.3 置信度表达

禁止所有对象都显示伪精确百分比。

应优先表达：

- qualitative level；
- supporting evidence count and quality；
- applicability match；
- known uncertainty；
- missing data；
- calibration eligibility；
- provenance。

## 十三、全局布局与视觉方向

### 13.1 总体风格

关键词：

- Scientific Mission Control；
- Research Operating System；
- calm；
- precise；
- evidence-dense；
- structured；
- professional；
- transparent；
- readable。

视觉身份固定为：

> **Scientific Instrument Workspace / Scientific Engineering Mission Control**

默认使用白色与冷灰色表面、克制的蓝色主交互、小圆角、细边框、清晰分隔、高信息密度和稳定状态色。整体更接近科研仪器控制台、IDE 与 Genome Browser，而不是通用 SaaS 管理后台。

同层级 Panel 不得用夸张阴影、渐变或尺寸互相争夺注意力。视觉重点必须来自任务优先级、选择状态、风险和待决策事项。

可以参考这些产品的产品思想，而不是直接复制外观：

- Benchling：科研对象和项目上下文；
- Galaxy：分析流程与可复现性；
- IDE：持续工作空间、层级导航与 Inspector；
- GitHub：版本、状态、Review 和历史；
- NASA mission control：态势、风险和决策；
- Genome browsers：高密度科学信息与上下文。

### 13.2 禁止风格

- ChatGPT 对话界面；
- 大面积营销 Banner；
- 黑金或霓虹 Cyberpunk AI 风；
- 玻璃拟态堆叠；
- 大量渐变；
- 无意义 3D DNA、细胞或粒子背景；
- 全页面卡片拼贴；
- 只有漂亮数字、没有科学对象；
- 以机器人头像表达 Agent 工作；
- 用动画掩盖等待、失败或 unavailable 状态。

### 13.3 信息密度

这是专业科研软件，不应过度留白，也不能把所有内容挤成表格。

采用渐进披露：

- 第一层：项目状态与可行动结论；
- 第二层：科学对象与关系；
- 第三层：证据、参数、版本和审计详情。

### 13.4 颜色语义

颜色必须服务于状态：

- neutral / informational；
- active；
- success / approved；
- caution；
- risk / rejected；
- blocked；
- stale；
- unavailable。

不要只依赖颜色传达状态；同时使用文本和图标。

### 13.5 图形使用原则

只在科学关系需要时使用可视化：

- DBTL cycle / workflow：阶段流；
- hypothesis：因果或比较视图；
- design：候选比较；
- metabolic intervention：通路上下文；
- simulation：baseline vs scenario；
- evidence：关系图或适用性矩阵；
- provenance：timeline / version graph。

禁止为每页强行加入 3D。

### 13.6 Design System Specification

Design System 必须集中定义并由 token 驱动，页面不得各自发明视觉规则。

**Grid 与空间**

- 12-column grid；
- 8px spacing 基线，允许 4 / 8 / 12 / 16 / 24 / 32 / 48；
- 默认圆角 6–8px；
- 默认边框 1px；
- 普通 Panel 主要用 border、spacing、surface 层级区分；
- shadow 仅用于浮层、拖拽和明确层级。

**Typography**

- Page Title；
- Section Heading；
- Panel Title；
- Body；
- Dense Body / Table；
- Label；
- Caption / Metadata；
- Mono / Identifier / Parameter。

ID、版本、参数、基因名和数值可使用等宽字体。中英文混排、上下标、希腊字母和生物学符号必须正常显示。

**Semantic color**

至少覆盖 neutral / information、supported / approved、uncertainty / warning、blocked / rejected、stale / superseded、model prediction、experimental observation、human-approved 和 unavailable。

模型预测、文献证据、实验事实和 AI proposal 必须有稳定且可区分的视觉语言，但不能只靠颜色区分。

**Icon 与 motion**

- 统一使用现有图标库；若无统一方案，优先 Lucide；
- 普通过渡建议 150–200ms；
- 动画只用于选择反馈、Panel 展开、状态变化和空间关系保持；
- 禁止循环或抢夺注意力的装饰动画；
- 必须支持 reduced motion。

Dark Mode 不是本阶段默认交付目标。只有现有项目已具备稳定主题系统时才保留和适配，不得因此延误核心架构。

### 13.7 Component Hierarchy

```text
L0  AppShell
L1  Route Workspace
L2  Scientific Panel
L3  Scientific Object View
L4  Object Inspector / Evidence Drawer
L5  Provenance / Evidence / Metadata Primitive
```

- L0 只负责全局导航、上下文、能力状态和布局插槽；
- L1 负责页面任务与数据编排；
- L2 负责一个清晰的科研职责；
- L3 必须绑定明确科学对象；
- L4 随 selection 工作，不复制主页面；
- L5 必须可跨页面复用。

禁止把业务请求、路由、完整布局和对象渲染堆进一个巨型组件。

## 十四、全局交互规则

### 14.1 Selection-driven workspace

用户选择一个 hypothesis、design、scenario 或 finding 时：

- 主画布更新选中状态；
- Inspector 显示详情；
- Evidence Drawer 切换到相关证据；
- URL 或可恢复状态更新；
- 不清空其他阶段上下文。

### 14.2 Progressive disclosure

默认显示：

- 可采取行动的结论；
- 关键证据；
- 关键风险；
- 当前状态。

展开后显示：

- 参数；
-完整来源；
- 版本；
- audit；
- 原始响应；
- 技术细节。

### 14.3 Approval interaction

关键审批必须：

- 显示将批准的具体版本；
- 显示未解决 critic findings；
- 显示风险和证据缺口；
- 要求或允许填写理由；
- 明确审批后工作流转移；
- 防止审批 stale 版本。

### 14.4 Loading / empty / error / unavailable

每个主要数据区域必须设计：

- loading；
- first-use empty；
- no-result；
- incomplete data；
- backend disconnected；
- permission denied；
- failed；
- unavailable；
- stale；
- partial result。

禁止将 empty state 统一写成 `No data`。

### 14.5 Language

架构必须支持中英文切换。

同一界面不允许无规则地中英文混排。

科研专有名词可保留英文，但标签、说明和操作语言必须服从当前语言设置。

## 十五、后端映射原则

### 15.1 先检查真实后端

在创建或修改前端代码前，必须检查：

- 现有前端目录；
- framework；
- router；
- component library；
- state management；
- API client；
- backend endpoints；
- WebSocket / event stream；
- data schema；
- generated types；
- authentication；
- existing visual assets；
- `.openai/hosting.json`（若存在，遵循对应托管流程）；
- current tests and build commands。

不得依据 Prompt 猜测 API 已存在。

### 15.2 建立 mapping matrix

为每个页面建立：

| UI domain | Required object | Real endpoint/schema | Status | Adapter needed | Mock allowed |
| --- | --- | --- | --- | --- | --- |

Status 至少使用：

- available；
- partial；
- absent；
- unclear；
- blocked。

### 15.3 前端 adapter

后端字段与前端 view model 不一致时，可以建立 typed adapter。

不得：

- 静默伪造字段；
- 将缺失数据填成看似真实的数字；
- 在生产路径中硬编码科学结论；
- 因前端方便而破坏后端 ID/version；
- 修改科学后端逻辑，除非用户明确授权。

### 15.4 Mock 数据规则

如果需要使用示例数据建立骨架：

- 必须集中管理；
- 必须标记 `DEMO` / `MOCK`；
- 不得与真实 API 数据混合；
- 必须可以一键关闭；
- 不得把示例运行标为真实项目；
- 示例建议使用 E. coli K-12 L-tryptophan 案例，但不得宣称是验证结果。

13. 保证现有前端仍可构建和运行；
14. 输出下一阶段 Page 1 详细设计所需的接口与问题清单。

### 17.2 本轮只做骨架，不做

- Page 1 最终视觉稿；
- Page 2 每个科学阶段的完整实现；
- 高保真代谢网络；
- 完整 3D E. coli；
- 复杂动画；
- Nanobanana 内容区生成；
- 所有后端能力的前端一次性接完；
- 登录、计费、营销页；
- 无后端支持的虚假工作流。

### 17.3 允许的骨架表现

骨架不是空白框。

每个一级页面至少应体现：

- 页面使命；
- 核心内容域；
- 主要任务入口；
- 与其他页面的关系；
- 数据状态；
- 后端可用性；
- 下一步详细设计锚点。

### 17.4 Phase 0 Completion Definition

只有以下条件全部满足，才可声明 Phase 0 完成：

- 四个一级页面及其路由真实存在且可访问；
- Workspace 五阶段处于同一持续工作空间，并共享 project / cycle / selected object；
- AppShell、导航和 context bar 不依赖页面内部硬编码；
- 深链接、刷新和浏览器前进后退不会丢失核心上下文；
- 至少一种真实后端数据完成端到端映射，其他能力明确标记 available / unavailable / mock；
- loading、empty、error、offline、permission denied、stale 状态可辨认；
- Evidence Drawer、Inspector、Human Gate 具备可复用骨架与清晰接口；
- 不存在伪装为真实结果的 demo 数据；
- 已执行仓库支持的 lint、typecheck、test、build，并记录结果；
- 已输出后端映射矩阵、遗留风险和 Page 1 / Page 2 下一阶段输入。

只有空路由不算完成；提前制作四个高保真完整页面也不属于本阶段目标。

## 十八、技术实现原则

- 优先复用现有技术栈和组件；
- 不因个人偏好重写前端；
- 使用可组合 Layout；
- 页面路由与科学对象状态解耦；
- 使用 typed API / view model；
- 避免巨型单文件组件；
- 避免每页复制状态 badge、provenance、evidence 组件；
- 对共享组件建立清晰边界；
- 保留后续页面级设计的扩展空间；
- 不提前锁死未知 API；
- 不允许仅凭视觉图覆盖已有可工作的交互；
- 不为了“完成”而移除现有功能。

### 18.1 Module Registry / Plugin-ready Architecture

“可扩展”不等于现在建设复杂插件平台。当前必须建立轻量 module registry / route configuration，使新增页面或 Workspace capability 原则上通过注册完成，而不是反复修改 AppShell。

每个模块注册项至少可表达：

- id；
- route；
- label；
- required project context；
- required backend capability；
- permission / role visibility；
- navigation visibility；
- loading / unavailable behavior；
- optional stage association。

要求：

- 新增普通页面不应修改 AppShell 核心结构；
- 新增 Workspace capability 不应复制整个 Workspace；
- navigation、route、capability state 不得维护三份互相漂移的硬编码列表；
- 当前只实现满足扩展边界的最小 registry，不建设超出需求的运行时插件系统。

建议的共享概念组件包括但不限于：

- ProjectContextBar；
- WorkflowStageRail；
- ScientificObjectHeader；
- StatusBadge；
- ProvenanceLink；
- EvidenceDrawer；
- ObjectInspector；
- HumanGatePanel；
- StaleWarning；
- CapabilityState；
- EmptyState；
- ErrorBoundary；
- VersionSelector。

组件名称可以按仓库规范调整，职责不能消失。

### 18.2 State Ownership Matrix

编码前必须建立并遵守以下状态归属：

| 状态类型 | 主要归属 | 示例 | 规则 |
| --- | --- | --- | --- |
| 可分享导航状态 | URL | project、cycle、stage、object、version、filter | 刷新与深链接可恢复 |
| 服务端事实 | Server state / query cache | design、evidence、approval、simulation result | 后端是 source of truth |
| 跨页客户端状态 | Global store | project context、capability status、临时 session | 仅保存无法由 URL 或服务端推导的跨页内容 |
| 局部交互状态 | Route / component state | panel width、展开项、hover、临时排序 | 不升级为全局状态 |
| 未保存编辑 | Form / draft state | design draft、review comment、test plan | 明确 dirty、saving、saved 和离开保护 |

禁止同一科学对象在 URL、global store 和 local state 中保留三份独立副本；禁止把 server response 无差别复制进全局 store；禁止使用 localStorage 作为科学数据 source of truth；禁止在无冲突策略时自动覆盖较新版本。

### 18.3 Performance Baseline

- 大型表格使用分页、服务端筛选或虚拟化，不一次渲染全部记录；
- Evidence Graph 设置默认节点与边上限，并支持聚焦扩展；
- Page 3、Page 4 的重型视图和可视化按需加载；
- simulation、graph、audit history 等长任务显示真实进度或不确定等待状态；
- 网络断开、超时与部分失败可辨认，并提供安全重试；
- 切换 selection 时避免重复请求，缓存 key 必须包含 project、object、version；
- 不以牺牲 provenance、版本正确性或数据新鲜度换取表面速度。

具体阈值在 Repository Audit 后依据真实数据规模确定，不得凭空承诺。

### 18.4 Change Safety Contract

- 先检查工作树和现有未提交修改；
- 复用现有技术栈、设计系统和可工作的功能；
- 采用小步、可验证改动，避免一次性大爆炸重构；
- 不覆盖、删除或格式化与本任务无关的用户修改；
- 不擅自修改后端科学逻辑、schema 语义、模型参数和数据库迁移；
- 共享接口变化优先通过兼容 adapter 控制影响；
- 不因检查失败而删除测试、降低类型约束或隐藏错误；
- 不创建第二套平行 AppShell、router、state framework 或 component library。

### 18.5 Conditional Audit Gate

Repository Audit 后默认继续安全施工，不因普通命名差异或可局部兼容问题反复询问。只有出现以下重大冲突才暂停：

- 需要覆盖或删除用户未提交工作；
- 需要替换核心技术栈或路由 / 状态框架；
- 需要修改后端科学逻辑、数据语义、鉴权或数据库结构；
- 真实仓库与本 Prompt 的核心产品前提根本不兼容；
- 无法在不伪造数据的前提下完成最低可用骨架；
- 需要凭证、外部权限或不可逆操作。

暂停报告必须包含事实、影响范围、已验证证据、安全备选方案和需要用户决定的单一问题。

## 十九、必须避免的架构错误

1. 把四个一级页面重新扩展成十多个一级菜单；
2. 把五个 Workspace 阶段拆成互不关联的页面；
3. 把首页做成通用 KPI Dashboard；
4. 把系统做成 ChatGPT clone；
5. 把 Knowledge 与 Provenance 做成两个重复资料库；
6. 把 Simulation 做成脱离设计对象的炫技页面；
7. 把 Evidence 只做成参考文献列表；
8. 只显示 AI 最终建议，不显示推理来源链；
9. 将模型预测和实验事实用相同样式呈现；
10. 隐藏 unavailable、out-of-domain 或失败状态；
11. 使用百分比制造虚假置信度；
12. 审批时不锁定对象版本；
13. 跳页后丢失 project / cycle / selection；
14. 用大量卡片替代信息架构；
15. 用硬编码 demo 答案冒充后端集成；
16. 为填满页面发明不存在的数据；
17. 优先美化而不验证数据结构；
18. 未经授权修改后端科学逻辑；
19. 在本阶段过早完成每一页高保真设计；
20. 宣称产品已经是完整 Virtual Cell 或 Digital Twin。
