## 3. 最终数据流与状态机

```text
Workflow Trigger / Project State
  → intake（Data Sufficiency Gate）
  → data_required（循环回 intake，直至补齐或人工升级）
  → observations_normalized（Observation Normalizer）
  → hypotheses_generated（Mechanism Graph + Competing Hypothesis Generator + Deduplicator）
  → evidence_assessed（Evidence Retriever/Assessor + HypothesisAssessment）
  → model_evidence_pending（可选：Model Adapter Registry 真实计算）
  → hypotheses_ranked（Conditional Ranker）⟲ model_conflicted（跨模型冲突时）
  → test_selection_required → test_planned（Diagnostic Test Selector + Execution Planner）
  → awaiting_test_result（**持久等待态**，可跨进程重启恢复）
  → belief_updated（Belief Updater，新证据 → 新版本，从不覆盖）
  → Stopping Gate → actionable | evidence_limited | human_review_required | ⟲ hypotheses_ranked
  → （actionable 时）Engineering Value Gate → handoff_ready
  → Diagnosis Handoff Gate → handed_off_to_design（真实触发问题1 WorkflowRun）
  → closed / reopen_diagnosis（版本号递增，回到 hypotheses_ranked）
```

`DiagnosisLoopController`（`harness/diagnosis/loop.py`）是 `DiagnosisSession.status` 的唯一写入点，与问题1 `WorkflowController`、问题2 `IterativeLoopController` 同构：单一状态写入者、`StageDefinition`-as-data 风格的合法迁移集合、每次迁移写入不可变 `DiagnosisTransition` 审计记录 + 一条 `ProjectEvent`。18 个状态全部实现（`intake`/`data_required`/`observations_normalized`/`hypotheses_generated`/`evidence_assessed`/`model_evidence_pending`/`hypotheses_ranked`/`test_selection_required`/`test_planned`/`awaiting_test_result`/`belief_updated`/`model_conflicted`/`human_review_required`/`actionable`/`evidence_limited`/`handoff_ready`/`handed_off_to_design`/`closed`）。

`awaiting_test_result` 的跨进程恢复能力已用真实的引擎重置（模拟进程边界）验证（`tests/diagnosis/test_loop.py::test_awaiting_test_result_survives_simulated_process_restart`），方法与问题2 `WAITING_FOR_RESULTS` 的验证方式一致。

```python
class ModelAdapter(ABC):
    def detect_capability(self) -> CapabilityStatus: ...
```

## 9. 端到端案例结果摘要

**案例 A（信息不足的 L-tryptophan 项目）**：仅给"提高 L-tryptophan 产量"+ 宿主时，Data Sufficiency Gate 返回 `insufficient`，状态机停在 `data_required`，非法转移守卫阻止其继续进入 `hypotheses_generated`；系统全程未创建任何 `DiagnosisDecision`，更未推荐 `aroG/trpE/tktA/ΔtnaA`（断言直接检查生成的假设语句不包含这些基因名）。

**案例 B（带时序和冲突证据的诊断）**：0h/20h/30h 三个时间点的滴度观测（先升后降，内部冲突）保持为 3 条独立 Observation，从未合并；机制图+竞争假设生成器产出跨越 `biological_mechanism`/`measurement_data` 等类别的假设集；两次真实 FBA 运行（不同氧气摄取边界）产生冲突结果（`convergence_status="conflicting"`），如检测到冲突则正确进入 `model_conflicted` 态；随后完成排序、选测试、进入 `awaiting_test_result`、摄入结果、`belief_updated`，最终 Stopping Gate 输出合法状态之一。

**工具不可用案例**：`vecoli`/`kinetic_resource` 两个 adapter 的运行结果 `runtime_status` 恒为 `not_computed`，`outputs={}`，从未被误报为 `optimal`。

## 10. 已知限制、未解决风险及其影响

- **无真实文献检索**：`EvidenceItem` 的 `source_type="literature"` 路径尚无真实检索工具支撑；当前只能通过 `expert_rule`/`llm_reasoning` 产生"待验证依据"，标注为低质量证据。风险：诊断的证据基础目前主要来自本地 DDR 知识库，覆盖面有限于已收录的 4 个产物。
- **规则式而非实时 LLM 假设生成**：与问题1的既定模式一致，为保证测试可复现性和确定性而选择；风险是生成的假设"创造力"上限受限于规则覆盖的知识库条目，`generation_provenance` 字段已为未来接入真实 LLM 生成留出扩展点。
- **vEcoli/kinetic 模型完全空缺**：任何依赖全细胞动力学模拟的诊断路径本轮无法真实计算，只能诚实标注 `unavailable`。
- **Problem 4 尚未独立实现**：当前用问题1引擎代替"Engineering Design"角色；一旦独立的问题4系统落地，`harness/diagnosis/handoff.py` 是唯一需要重新指向的位置，但届时需要重新验证 `DiagnosisDecision` 到新系统输入格式的映射是否仍然成立。
- **多用户并发治理未扩展到诊断层**：问题2已有的乐观并发（`Project`/`IterativeCycleState`）未在 `DiagnosisSession` 上验证并发冲突场景（`DiagnosisSession` 确实有 `version` 字段，但本轮测试未覆盖并发写入冲突的显式断言）——后续应补齐一个类似问题2 `test_concurrency.py` 的诊断层测试。
- **前端仍是纯 API**：与问题2一致，本轮未新建诊断相关的前端面板，`web/index.html` 未改动。

## 14. 最终判断

问题3完成后，系统具备了从异构观测形成竞争机制假设、用真实证据和真实模型（cobrapy FBA）约束假设、选择判别性实验、追加式更新信念、在明确的 Stopping/Engineering-Value/Human Gate 后才允许触达"Engineering Design"（当前由问题1引擎承担）、并将全过程写回问题2 Memory 账本的完整闭环。三层控制器（问题1 `WorkflowController`、问题2 `IterativeLoopController`、问题3 `DiagnosisLoopController`）架构同构、持久化基底统一（同一 SQLite 文件、同一事件账本），不存在互不连接的第二套历史存储。

但仍需诚实限定：本轮的竞争假设生成是确定性规则式的，不是实时 LLM 推理；真实模型能力目前只覆盖 GEM/FBA 一类（vEcoli、动力学/资源分配模型仍诚实降级）；Problem 4 尚无独立实现，当前由问题1引擎代为承担"Engineering Design"角色。这些限制均在第10节如实列出，不构成"假装已完成"的掩盖。
