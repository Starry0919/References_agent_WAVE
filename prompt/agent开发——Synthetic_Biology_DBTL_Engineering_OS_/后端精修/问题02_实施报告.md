## 1. 架构审计:原系统为何是 one-shot,状态在哪里丢失

在改代码前审计了现有代码和问题 1 已实现的 Workflow Engine:

- **`harness/workflow/controller.py`(问题 1)**:`WorkflowController` 把持久化
  硬编码为 JSON 文件快照(约 10 处直接调用 `checkpoint.save(run)`),没有任何
  存储抽象层。它的 `Stage` 枚举/`STAGE_DEFINITIONS`(`definitions.py`)是
  synbio 流水线专用的(INTAKE..REPORT)。它的 `StageOutcome`/`GateContext`/
  `ApprovalRecord`/`PendingRequest`/`ApprovalDecision`(`contracts.py`)类型
  已经是通用的、非 synbio 专属的,可以直接被问题 2 的新 Gate 复用。
- **问题 1 的 `WorkflowRun` 只处理 Execution State**:一次运行从创建到完成/
  失败/暂停都在一个进程的生命周期内(毫秒到分钟级),`checkpoint.py` 的
  JSON 快照对这个生命周期完全够用,但从未被设计成要在"进程完全退出、数天
  后才收到实验结果"的场景下存活——这正是问题 2 的 `WAITING_FOR_RESULTS`
  必须满足的场景。
- **状态丢失的具体位置**:仓库里不存在任何关系型数据库、ORM 或迁移工具;
  项目级事实(谁在何时提出过什么设计、构建成功与否、测到了什么、为什么
  改变判断)完全没有持久层——每次对话都是从零开始的一次性报告生成,
  聊天记录本身被当成了"记忆",而聊天记录既不区分"用户说过的话"和"经实验
  验证的事实",也无法在关闭进程后被结构化地恢复。

## 3. 数据模型与迁移

- **存储**:SQLAlchemy 2.0 ORM,dev 环境 SQLite(`project_ledger.db`,已
  gitignore),schema 全部使用可移植类型(`String`/`Float`/`Integer`/`JSON`),
  为后续切换 PostgreSQL 预留(连接串改变,不需要重写 schema)。
- **迁移**:`harness/migrations.py` 提供一个最小手写版本化迁移器
  (`schema_migrations(version, applied_at)` 表跟踪,每个迁移各自一个事务,
  重复调用幂等)。迁移 0001 用 `Base.metadata.create_all` 定义——因为本轮
  全部 28 张表都是全新的,没有存量数据需要迁移;未来对已有数据表做增量
  演进时应该手写 ALTER 语句,而不是再次整体 `create_all`。
- **已知限制**:SQLite 的 `ALTER TABLE` 能力有限,一旦下一轮需要对已有表做
  实质性列变更,这个手写迁移器会不够用,需要引入 Alembic——这是刻意记录
  的、非无限期搁置的技术债,不是被忽略的问题。
- **字段级不可变性**:不是靠"约定不去改"这种口头约束,而是
  `harness/db.py::guard_immutable_fields` 注册的 SQLAlchemy `before_update`
  监听器,任何代码路径尝试修改被保护字段都会抛出 `ImmutableFieldError`——
  已用测试直接验证(见 §6)。
- **乐观并发**:`Project`/`IterativeCycleState` 都有整数 `version` 列,
  `harness/db.py::check_and_bump_version` 在写入前比较调用方携带的
  `expected_version`,不一致则拒绝(`ConcurrencyConflictError`),绝不静默
  覆盖。

## 4. DBTL 状态图

```
PROJECT_CONTEXT_READY
  → DESIGN_BASELINE_CAPTURED
  → DESIGN_PROPOSED                    (可从 REDESIGN_OR_STOP_DECISION 循环回到这里)
  → HUMAN_DESIGN_GATE                  [pending_gate: approval]
  → BUILD_TEST_HANDOFF
  → WAITING_FOR_RESULTS                (SQL 持久,可跨进程重启存活数天)
  → DATA_INGESTION                     (恢复点)
  → DATA_QC                            [Data QC Gate]
  → OBSERVATION_EXTRACTION
  → RESULT_INTERPRETATION
  → HYPOTHESIS_UPDATE                  [Hypothesis Update Gate]
  → FAILURE_OR_SUCCESS_CLASSIFICATION
  → LEARNING_UPDATE_GATE               [Policy Update Gate]
  → REDESIGN_OR_STOP_DECISION
  → (DESIGN_PROPOSED 新版本 | PROJECT_PAUSED | PROJECT_COMPLETED)
```

- `IterativeLoopController` 是 `IterativeCycleState.current_state` 的唯一
  写入点;每次转移都检查"当前状态是否在合法的 from_states 集合内",不合法
  抛 `IllegalCycleTransitionError`;每次转移写一条不可变
  `IterativeCycleTransition` 审计记录 + 一条 `CYCLE_STATE_CHANGED` 事件。
- 与问题 1 不同,这里大多数状态对应真实世界事件(人工批准设计、湿实验室
  数天后报告结果),因此不是"跑一个 `advance()` 循环直到终止",而是暴露
  一个个具名转移方法(`propose_design`、`enter_waiting_for_results`、
  `begin_data_ingestion`……)——单一写入者、Gate 判定、持久审计这些安全
  属性和问题 1 相同,只是适配了"事件驱动、跨天等待"的形状。
- **Gate 拒绝 = 转移从未发生**:`GateRejectedError` 在状态被修改前抛出,
  已用测试验证被拒绝的转移不会把 `current_state` 改到一半。
- **NEW_DESIGN_VERSION 的实现**:doc 把它列为 REDESIGN_OR_STOP_DECISION 的
  三种去向之一(与 PROJECT_PAUSED/PROJECT_COMPLETED 并列),本实现将其
  实现为直接迁移回 `DESIGN_PROPOSED`(下一个真实状态),而不是一个专门
  停留的状态——因为 doc 原文把它描述为"决策解决成什么",不是"停留在哪"。

### 过程发现的真实问题(如实记录,而非事后包装成"设计如此")

1. **路由顺序 bug**:`GET /api/designs/{design_version_id}` 注册在
   `GET /api/designs/diff` 之前,导致对 `/designs/diff` 的请求被
   `{design_version_id}` 模式先匹配、把 `"diff"` 当成了设计版本 id。这是
   在真实服务器上手动跑通"创建 v0→导入结果→生成 v1→查看 diff"全流程时
   发现的(不是单元测试发现的,单元测试当时还没覆盖真实 HTTP 路由匹配
   顺序)——已修复(把固定路径路由移到参数化路由之前),并补充了
   `tests/projects/test_api.py::test_design_diff_route_is_not_shadowed_by_parameterized_route`
   作为回归测试。
2. **SQLite 自增列设计错误**:最初把 `ProjectEvent.event_id`(字符串)设为
   主键、把 `seq`(整数,用于保证回放顺序)设为普通 `autoincrement=True`
   列——SQLite 只保证真正的整数主键自增,导致 `seq` 恒为 `NULL` 并触发
   `IntegrityError`。修复为 `seq` 是整数主键,`event_id` 是唯一索引的业务
   标识列。
3. **`BiologicalRuleGate` 与已批准豁免脱节**(继承自问题 1 的设计评审,
   在本轮集成测试中再次验证):必需基因敲除即使已获批准,Gate 仍会持续
   报告该违规,聚合逻辑会一直卡在 `human_review`——这个问题在问题 1 阶段
   已发现并修复,问题 2 的测试重新确认了修复仍然有效。
4. **`Observation` 更新竞态与 SQLite 文件句柄**:在 Windows 上连续多次跑
   完整测试套件时,出现过一次(约 10 次运行中 1 次)间歇性失败,单独跑
   对应测试文件从不复现。根因判断为 `reset_engine_for_tests` 没有显式
   `dispose()` 旧 engine,导致上一个测试的 SQLite 文件句柄可能在 Windows
   上比预期晚释放。已修复为显式 `dispose()`,修复后连续 5+ 次全量重跑
   均 100% 通过。

### 集成场景(doc 18.2-18.5,全部通过)

- **场景 A(L-色氨酸两轮 DBTL)**:v0(`trpE S40F + AnTrpC replacement +

  (`technical_failure_cannot_drive_policy`),不论证据数量或是否有人工

全新的 `python main.py` 进程 → `GET .../cycle` 仍返回
`WAITING_FOR_RESULTS` 及此前的 `active_design_version_id`/
`active_experiment_plan_id` → `POST .../cycle/begin_data_ingestion`
成功推进到 `DATA_INGESTION`。

## 8. 未完成能力(如实标注,不冒充已实现)

- **真实 Bayesian optimization / active learning**:`strategy_router.py`
  只做规则路由,`route_strategy()` 在应该用 BO 的场景会诚实返回
  `implemented=False` 并降级到 mechanistic_rules,不伪造一个优化器调用。
- **真实预测性细胞模型**:`ModelVersion`/`Prediction`/`Residual` 只是裸
  ORM schema,没有服务层,因为本轮(以及问题 1)都没有接入真实机制模型——
  与问题 1 `ModelApplicabilityGate` 诚实标注"未注册模型"一致。
- **`PortfolioView`**:doc 6.9 要求的跨项目知识查询层本轮**未实现**——
  `KnowledgeClaim` 的晋升阶梯和独立性检查已完整实现,但一个专门的只读
  跨项目聚合视图/端点这一轮没有构建,是本报告明确标注的缺口,而非疏漏。
- **完整 RBAC/ABAC**:只有 `Actor`(id/type/role)+ 乐观并发 +
  "提出者不能自批准"这三项最小协作治理,没有实现完整的基于角色/属性的
  权限引擎。
- **真实外部 LIMS/库存集成**:`ProtocolVersionRef`/`PhysicalStockRef` 只是
  引用字段的 schema,没有对接任何真实外部系统;`availability_status` 没有
  任何代码路径会在未经外部确认时写入。
- **Alembic 迁移**:见 §3,已作为已知限制记录,不是无限期搁置。
- **omics 解析器**:本轮只实现了两个具体解析器(growth/titer CSV、
  genotype-verification CSV),因为这是集成场景 A/B 直接需要的两种;
  proteomics protein matrix 等其他 doc 11.1 列出的类型未实现具体解析器
  (接口 `DataIngestor` 已就位,可插入新解析器而不改动编排逻辑)。
- **前端可视化**:本轮明确 API-first,`web/index.html` 未新增 Project
  Status/Design Lineage 等面板(与用户确认过的范围裁剪,见对话记录)。

## 9. 风险与后续

- **数据质量**:目前的 QC 规则(负值排除、单次重复警告)是演示级的,
  真实项目需要按 assay 类型定制更严格的 QC 规则集。
- **因果归因**:`outcome_classifier.py` 的方向/效应量比较是启发式的
  (百分比变化 + 约束阈值),不是统计显著性检验;`causal_confidence` 目前
  由调用方直接指定,没有从样本量/方差自动计算的机制。
- **跨项目知识迁移**:`KnowledgeClaim` 的独立性检查目前只区分"同一批次
  vs 不同批次",没有校验"跨宿主/培养基/组合基因型传播需要显式降级"这条
  doc 6.8 提到的规则——当前实现依赖调用方在 `scope` 字段里如实填写条件,
  没有程序化强制降级逻辑,这是后续应该补的一层。
- **自动实验边界**:全系统没有任何代码路径可以触发真实的湿实验室动作或
  设备操作——`ExperimentRun`/`GenotypeVerification` 全部由人工通过 API
  登记结果,这是刻意的边界,不是未完成的功能。
- **并发治理的深度**:目前的乐观并发覆盖 `Project`/`IterativeCycleState`
  两张表;`DesignVersion`/`KnowledgeClaim` 等其他可能被多人同时操作的表
  还没有同等的版本字段,严格来说多人同时对同一 `KnowledgeClaim` 提出
  晋升请求存在竞态窗口(概率低,后续应补齐)。

## 11. 最终判断

问题 2 完成后,系统从"AI Biology Design Report Generator"升级为一个真正
持久化的项目账本:项目、设计版本、假设、失败案例和知识主张全部可版本化
追溯、可从事件账本重建,`WAITING_FOR_RESULTS` 已用 OS 级别的真实进程
终止/重启验证过跨天存活能力。问题 1 的 Workflow Engine 作为
`DESIGN_PROPOSED` 状态的具体实现被真实复用(而非并列重造),`RunStore`
接口抽取让这种复用是字面上的代码依赖,不只是架构上的相似。

但仍需诚实限定:本轮完整实现了 Memory 持久层和 Iterative Design Loop,是
朝 AI Virtual Cell 演进的必要条件,不等于已经拥有完整 Virtual Cell、
真实 optimizer、真实预测模型或无人监管的自驱动实验室——这些在 §8/§9
中逐项标注为未完成能力和已知风险,而非被掩盖。
