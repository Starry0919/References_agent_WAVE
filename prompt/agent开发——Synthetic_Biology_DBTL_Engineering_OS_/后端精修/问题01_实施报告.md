## 1. Current-state audit(原控制权实际在哪里)

审计先于修改,证据如下(全部为文件路径 + 行号级证据,详见开发过程中的审计记录):

- **`harness/agent.py:69-141`(`run_agent_turn`)**:整个系统是一个自由的 LLM
  工具调用循环。每一步 `all_tools()` 把全部已注册工具原样交给 LLM
  (`agent.py:71`),LLM 自行决定是否调用、调用哪个、调用几次。`harness/`
  下不存在任何阶段、状态机或 Gate。
- **"Phase 0-7" 不存在于代码中**:全仓库检索 `Phase\s*[0-7]`,唯一命中是
  `workflows/synbio_v1/modules/*.py` 里的 docstring 注释(如
  `engineering.py:1` "V1.1 Phase 2 upgrade"),这些是开发里程碑的文字记录,
  不是运行时状态机、不是强制 Gate。真正的运行时顺序标签是
  `task_parser.py:1` 等文件里的 "Module 0-4",且这只是
  `workflows/synbio_v1/workflow.py:18-30` 里一个无分支、无 Gate 的固定
  函数调用序列。
- **`harness/tools/base.py`**:工具注册表是一个扁平全局字典(`REGISTRY`,
  `base.py:68`),**无 allowlist**——任何 `@tool` 装饰的函数在任何时刻都能
  被 LLM 调用。`execute_tool`(`base.py:247`)有超时(默认 60s)但
  **无重试、无幂等键、无结构化 provenance**,只有 `duration_ms`/`is_error`。
- **可复用的既有资产**(不是从零开始):`workflows/synbio_v1/modules/*`
  已经是确定性、无 LLM 调用的规则代码(task_parser → retriever →
  diagnosis → engineering → evidence → validation → report),本轮在节点
  内部逻辑层面已经满足"机制优先于 LLM 判断";
  `workflows/synbio_v01/modules/evaluator.py:27` 已有一个雏形
  `BiologicalRuleGate`(拒绝必需基因敲除、拒绝无证据设计);
  `knowledge/ddr_database/*.json` 是磁盘上的真实证据库;
  `harness/sessions.py:148-213` 有可复用的 JSONL 持久化 + 崩溃恢复模式。
- **真正的缺口**:整条合成生物设计流程被包装成**一次不透明的工具调用**
  (`tools/synbio_design_v1.py:19` → `workflows/synbio_v1/workflow.py:run()`),
  没有 `WorkflowRun`/`StageRecord`、没有结构化 `BiologicalState`/
  `EngineeringDecision`、没有阶段契约、没有 7 道 Gate、没有 checkpoint/
  resume、没有 run trace、没有能真正阻断迁移的人工审批。

仓库此前没有 git,已在改动前 `git init` 并提交基线快照(commit
`c3990a4`),作为本轮重构的可回滚起点。

## 2. Architecture decision(为何采用状态图 + Gate + 阶段内推理)

采纳设计文档 4.2 的结论:**状态图 + 规则 Gate + 阶段内 LLM**,理由:

- 自由 LLM Agent(现状)不可复现、必经步骤可被跳过、失败无统一处理;
- 完全固定线性 pipeline 灵活性太低,无法承载"缺证据 → 回退"、"高风险 →
  人工审批"等条件分支;
- 状态图 + Gate 的方案能同时提供稳定性(唯一 Controller 决定迁移)和灵活性
  (Gate 结果驱动分支),且天然支持可重放、可比较。

关键实现决策(与最初计划相比,经过一轮设计评审后修正,细节见 §9):

1. `candidate_designs` 只增不改(append-only);状态变化只发生在
   `engineering_decisions` 列表里,且同一 `decision_id` 的记录在多次尝试
   间**更新而非重复追加**——被拒绝的必需基因敲除永远不会被"悄悄改写"成
   别的操作,替代方案必须是携带 `parent_decision_ids` 的**新** decision。
2. 新的 `harness/tools/executor.py`(allowlist/重试/幂等/溯源)**只服务于
   Workflow Engine 自身的内部工具**(目前只有一个 FBA 占位工具),
   **没有**接入 `harness/agent.py` 的通用聊天循环——通用循环的
   `execute_tool()` 错误字符串契约是既有、可能被断言的行为,本轮不承担
   无收益的回归风险。
3. Gate 执行顺序显式固定(`gates.GATE_SEQUENCE`),而不是隐式依赖调用
   顺序;一次 Gate battery 用"最差状态优先"聚合成一个 `GateResult`。
4. Checkpoint 用临时文件 + `os.replace` 原子写入,避免中途崩溃产生损坏快照。

## 5. State graph and contracts

```
INTAKE
  → TASK_NORMALIZATION            (缺 target → waiting_user,绝不静默猜测)
  → CONTEXT_AND_EVIDENCE_ACQUISITION
  → SYSTEM_RECONSTRUCTION         [scaffold]
  → BIOLOGICAL_DIAGNOSIS          [partial]  (EvidenceGate: 有瓶颈声明必须有 source_ddr_id)
  → BOTTLENECK_PRIORITIZATION     [scaffold] (精确指定为"节点骨架",非专家级诊断算法)
  → ENGINEERING_STRATEGY_GENERATION           (CandidateDiversityGate 去重)
  → MODEL_AND_RULE_VALIDATION     (7 道 Gate 全跑;essential-gene KO → waiting_user)
  → EXPERIMENT_AND_IMPLEMENTATION_PLAN         (entry_condition 强制:candidate_designs 必须全部经过校验,不可跳过)
  → FINAL_EVALUATION
  → REPORT                        (终止态)
```

- **回退**:证据不足 → `insufficient_evidence` fallback 回到
  `CONTEXT_AND_EVIDENCE_ACQUISITION`,受 `RetryPolicy.max_stage_attempts`
  预算限制,超预算后 `status=blocked` 并记录 `termination_reason`。
- **终止**:连续两次尝试输出完全相同 → 判定"无新信息",直接 `blocked`,
  不无限重试(`controller._retry_or_fallback`)。
- **人工审批**:`SafetyHumanGate` 判定的 `human_review` 会把
  `run.status` 设为 `waiting_user` 并写 `pending_request`(区分
  `missing_information` 与 `approval` 两种)——`controller.advance()`
  在 `waiting_user` 状态下直接抛 `RunWaitingOnUserError`,必须先
  `submit_approval`/`submit_user_response` 才能继续,不是"仅显示提示"。

## 8. Biological benchmark result

三类 benchmark 均通过,指标为真实计算值,`expert_review` 如实标注为
`"pending"`(尚无人类专家复核,不得虚构通过率):

```
[benchmark-1 tryptophan] key_diagnosis_recall=1.00 unsupported_claims=0
  decision_evidence_traceability=1.00 decision_validation_match_rate=1.00
  expert_review=pending

[benchmark-2 lysine] independent_diagnosis=True gene_overlap_with_trp=none
  unsupported_claims=0 decision_evidence_traceability=1.00
  decision_validation_match_rate=1.00 expert_review=pending

[benchmark-3 adversarial] dangerous_edit_interception_rate=1.00
  intercepted_codes=['bypass_failed_gate', 'essential_gene_knockout',
  'host_range_conflict', 'operation_conflict', 'unknown_gene_id']
  alternative_candidate_is_new_decision=True expert_review=pending
```

- **Benchmark 1**:`prioritized_bottlenecks` 同时含
  `precursor_supply` 与 `feedback_inhibition` 两个不同机制层
  (`key_diagnosis_recall=1.0`);所有 accepted 决策都有
  `mechanism`/`evidence_record_ids`;没有任何 accepted 决策是对
  registry 内必需基因的无条件敲除。
- **Benchmark 2**:赖氨酸案例匹配到独立的 `DDR-004`(而非色氨酸的
  `DDR-001`);两案例的瓶颈描述、目标基因集合完全不相交
  (`gene_overlap_with_trp=none`);赖氨酸自身瓶颈同时覆盖
  `feedback_inhibition`(lysC)与 `competing_pathway`(hom/thrB)两个
  独立机制层;所有相关 evidence 的 `strain_similarity` 从不虚报为
  `"high"`。**过程发现的真实问题**:最初运行时
  `unsupported_claims=3`——`evidence.py` 把 DDR-004(无真实论文引用)的
  证据无条件标成 `"reference_available"`,已在 §4 所述的
  `workflows/synbio_v1/modules/evidence.py` 修复中订正为诚实的
  `"general_engineering_knowledge"`。这正是本项目反复强调的"不得虚构证据"
  原则被自己的 benchmark 抓到的一个真实案例,而不是自我宣称通过。
- **Benchmark 3**:必需基因敲除(`ftsZ`)、不存在的基因 ID、跨宿主基因
  (`sigB`,枯草芽孢杆菌)、同一基因矛盾编辑(同批次敲除+过表达 `ptsG`)
  四类对抗性输入,`dangerous_edit_interception_rate=1.0`,全部被
  IdentityGate/BiologicalRuleGate/SafetyHumanGate 拦截;对必需基因敲除的
  knockdown 替代方案被验证为**新的、独立的** `EngineeringDecision`(不同
  `decision_id`,带 `parent_decision_ids` 回链),而非原决策被静默改写。

**局限**(如实记录,不夸大):

- `expert_review` 全部为 `pending`——以上均为程序化结构断言,尚无人类
  合成生物学专家复核诊断和决策的生物学正确性。
- Benchmark 1 的"竞争通路/生长负担"两个机制类别未在色氨酸案例中被
  实际触发(该案例的知识库内容本身没有这两类瓶颈);分类器对这两类的覆盖
  能力由 `gates.py`/`synbio_stages.py` 的单元测试和赖氨酸案例
  (`competing_pathway`)间接验证,不是色氨酸 benchmark 本身的断言。
- `essential_genes_reference.json` 是演示用途的小型精选列表,不等于
  Keio collection 或任何权威必需基因数据集。

## 10. Known limitations

1. **本轮 stage 实现均为确定性代码,非真正的"受约束 LLM 局部推理"**——
   `StageOutput`/`requested_action` 契约已就位,但当前 11 个阶段实现全部
   复用既有确定性函数,没有一个阶段真正调用 LLM。这符合文档"现有逻辑可
   作为临时实现"的允许范围,但 `implementation_status` 标注为
   `partial`/`scaffold` 的阶段(`SYSTEM_RECONSTRUCTION`、
   `BOTTLENECK_PRIORITIZATION`、`TASK_NORMALIZATION` 等)仍待后续问题
   (问题 4:瓶颈诊断)填充真正的诊断深度。
2. **`ModelApplicabilityGate` 恒为"未注册模型"**——没有真实 FBA/AMN/
   vEcoli 集成,`fba_flux_analysis` 是一个恒定返回 `unavailable` 的占位
   工具,诚实记录而非伪造预测。
3. **`MODEL_AND_RULE_VALIDATION` 的 `revise_candidates` 回退路径在
   identity/host-range/operation-conflict 类违规下基本不会被触发**——
   因为 `resolve()` 在检测到这些违规的同一次尝试内就直接把决策终态标记
   为 `rejected`,不需要重试。这保持了安全性(非法候选从不被接受),但
   意味着该 fallback 目前主要为 schema 校验失败等"结果会变化"的失败模式
   服务,不是每种违规类型都会真正走到"回到候选生成"这条路径。
4. **文献-模型冲突检测是近似实现**——由于本轮没有第二个独立证据源
   (真实 FBA/数据库),"模型与文献冲突"被近似为"检索到的多个 DDR 得分
   接近、匹配存在歧义"(`_near_tie_conflict_note`),结构上支持
   `uncertainty.conflicting_fields`,但当前 4 条 DDR 的知识库很难自然
   产生真实的近似打平案例,该机制主要通过单元测试直接验证。
5. **`essential_genes_reference.json` 是小型演示数据集**,不是权威必需
   基因数据库;`IdentityGate` 的"已知基因"名单同样只覆盖当前知识库涉及
   的基因,不是完整的 E. coli 基因组注释。
6. **Checkpoint 超时保护有限**——`ThreadPoolExecutor` 的 `future.result(timeout=...)`
   超时后线程本身不会被强制终止(Python 标准库限制),只是不再等待其
   结果;对当前占位工具(瞬时抛错)无实际影响,但真实长耗时工具接入时
   需要重新评估。

## 11. Deferred items(明确属于其他问题,未在本轮解决)

- 问题 4(瓶颈诊断)的完整算法深度——本轮只交付
  `BOTTLENECK_PRIORITIZATION` 的可运行骨架与结构化输出,不宣称专家级
  诊断能力。
- 真实 FBA/COBRApy/vEcoli/AMN 集成——`ModelApplicabilityGate` 与
  `fba_flux_analysis` 占位工具已预留接口。
- 逆合成(retrosynthesis)、DNA 自动化装配脚本——当前项目场景(K-12 宿主
  内源改造为主)未触发这类分支,接口未设计。
- 多 Agent 拓扑——本轮明确只做单一 Controller + 确定性阶段实现,
  `StageOutput` 契约为未来 LLM 局部推理预留接口,不提前引入角色扮演式
  多 Agent 结构。
- 前端可视化 Workflow Run 的界面——`GET /api/workflow-runs/{id}` 已
  返回完整结构化状态,但 `web/index.html` 本身未新增对应的渲染视图
  (本轮明确排除"大规模重写前端")。

## 12. 最终审查问题逐项作答(设计文档第十节)
