# Synthetic Biology Agent V1.1 Optimization Specification


# 1. Project Status


The Synthetic Biology Agent V1 prototype has been successfully implemented.


Current capabilities:

- User biological task understanding
- DDR knowledge retrieval
- Biological bottleneck reasoning
- Engineering strategy generation
- Evidence grounding
- Final report generation


Example test:

Input:

"Design an E. coli K-12 strain for improved L-tryptophan production."


Current workflow:


User Query

↓

Task Parser

↓

DDR Retrieval

↓

Biological Reasoning

↓

Engineering Strategy

↓

Evidence Evaluation

↓

Report



The current architecture is correct.


DO NOT replace the architecture.

Only improve internal modules.



# 2. V1.1 Main Objective


Upgrade the Agent from:


"DDR-based reasoning assistant"


to:


"Evidence-grounded synthetic biology engineering assistant"



The key improvement:

Move from:

Paper summary level knowledge


to:


Engineering decision level knowledge.



# 3. Optimization Strategy


Implement improvements in independent phases.


Priority order:


Phase 1:

Knowledge Base Architecture Upgrade


Phase 2:

Engineering Action Library


Phase 3:

Evidence Quality System


Phase 4:

Experimental Validation Module


Phase 5:

Final Report Optimization



Complete one phase before starting the next.



# Phase 1
# Knowledge Base Architecture Upgrade



## Current Problem


Current DDR structure contains:


- engineering problem
- diagnosis
- engineering actions
- general rules


However, it lacks separation between:


1. Paper evidence

2. Expert reasoning

3. Engineering operation



Therefore future retrieval cannot distinguish:

"what was experimentally proven"

from:

"what is a generalized engineering rule"



## New Knowledge Architecture



Upgrade knowledge structure to:


```

knowledge/

├── papers/

│
│   ├── paper_metadata.json
│
│   └── experimental_evidence.json

├── ddr_database/

│
│   └── DDR_xxx.json

├── engineering_actions/

│
│   └── action_database.json

└── biological_rules/

```
└── rules.json
```

````



# Layer 1
# Paper Evidence Layer


Purpose:

Store experimentally verified information.


Schema:


```json
{
"paper_id":"",

"title":"",

"authors":"",

"journal":"",

"year":"",

"doi":"",

"organism":"",

"host":"",

"product":"",

"engineering_methods":[],

"experimental_results":[]

}
````

Example:

Xiong 2021:

Should store:

* E.coli strain information
* gene modifications
* fermentation results
* measured production

Do not store interpretation here.

---

# Layer 2

# DDR Reasoning Layer

Purpose:

Store expert reasoning chain.

Schema:

```json
{

"ddr_id":"",

"problem":"",

"observation":"",

"hypothesis":"",

"engineering_logic":"",

"general_rule":""

}

```

Example:

Problem:

PEP/E4P limitation

Observation:

Aromatic amino acid pathway requires central carbon precursors

Hypothesis:

Redistribute carbon flux

---

# Layer 3

# Engineering Action Layer

Purpose:

Convert reasoning into executable engineering knowledge.

Example:

Instead of:

"Improve carbon flux"

Store:

```json
{

"action_id":"",

"action_type":

"transport engineering",


"target_gene":

"ptsG",


"modification":

"knockout",


"replacement":

"glf expression",


"biological_effect":

"reduce PEP consumption",


"applicable_conditions":

[
"PEP limitation",
"aromatic amino acid production"
]

}

```

This layer is essential for generating real gene modification suggestions.

---

# Phase 2

# Engineering Action Library

Implement a reusable engineering action database.

Supported modification categories:

## Knockout

Example:

```
gene deletion
remove competing pathway
```

## Overexpression

Example:

```
increase pathway capacity
```

## Promoter engineering

Example:

```
increase expression dynamically
```

## Transport engineering

Example:

```
PTS replacement
nutrient uptake modification
```

## Heterologous pathway introduction

Example:

```
new biosynthetic capability
```

Each action must include:

* target
* mechanism
* expected effect
* risk
* evidence

# Phase 3

# Evidence Quality System

## Current Problem

Current output:

```
confidence: medium
```

is insufficient.

Implement:

```json
{

"evidence_quality":{

"literature_support":"",

"mechanistic_support":"",

"strain_similarity":"",

"transferability":""

}

}

```

Example:

Xiong 2021:

Literature support:

High

Mechanistic support:

High

Strain similarity:

Medium

Transferability:

Medium

Reason:

Paper used E.coli MG1655 derivative, user requested E.coli K-12.

# Evidence Rules

The Agent MUST NOT fabricate:

* papers
* DOI
* authors
* database records
* experimental results

If information is not verified:

Return:

```
evidence_status:
unknown

reference:
null

confidence:
low

```

# Phase 4

# Experimental Validation Module

## Current Problem

Current validation is too general.

Example:

"measure metabolites"

Not enough.

Upgrade validation generation.

Validation should contain four levels:

## Level 1

Genotype Validation

Examples:

* PCR
* sequencing
* genome verification

## Level 2

Mechanism Validation

Examples:

* metabolite measurement
* enzyme activity
* flux analysis

## Level 3

Phenotype Validation

Examples:

* titer
* yield
* productivity
* growth

## Level 4

Trade-off Analysis

Examples:

* growth burden
* byproduct formation
* substrate consumption

Schema:

```json
{

"validation_plan":{

"genotype":[],

"mechanism":[],

"phenotype":[],

"tradeoff":[]

}

}

```

# Phase 5

# Final Report Optimization

Current report:

Too focused on limitations.

Change structure:

```
1. Engineering Objective


2. Relevant DDR Evidence


3. Biological Bottleneck


4. Engineering Design


5. Evidence Quality


6. Validation Plan


7. Limitations

```

Move:

"V1 knowledge base limitation"

to:

"System limitation"

Do not mix system limitations with biological conclusions.
